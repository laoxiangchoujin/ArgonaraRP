## `_RECEIVE_SHADOWS` 与 deferred 的"为什么居然有阴影"（2026-09-12，结论）
- Runtime 里**没有任何地方**开启 `_RECEIVE_SHADOWS`（只有 `_LIGHTS_PER_OBJECT` / `_USE_DEBUG` 是 C# 显式控制的）。
  它是**非 local 的关键字**：材质上 `Material.EnableKeyword` 会让它在绘制时按全局状态生效，而且**会一直留着** →
  最可能的解释：Lit 材质（Receive Shadows 默认勾选）在 deferred 光照 pass **之前**刚被绘制过 → 关键字泄漏过去 → 所以 deferred 看起来有实时阴影。
  **是"碰巧能跑"**：材质勾选关掉/绘制顺序变化就会突然没阴影。
- 用户的看法（"逐材质控制就够了，可能没必要全局控制"）**基本成立**：deferred 全屏 pass 本来就没有"逐物体"概念（他们注释里也写了只做全局控制）。
- 结论/建议：① 屏幕空间 pass 里**不要**用 `_RECEIVE_SHADOWS` 做早退（现状就是不判断，最稳）；② 若真想要一个"全局接收阴影"开关，用 uniform 判断，**不要**全局 `Shader.EnableKeyword`（会破坏 forward 的逐材质勾选）。
- 一分钟验证法：把 `GetDirectionalShadowAttenuation` 开头的 `#if !defined(_RECEIVE_SHADOWS)` 改成 `#if 1`（强制 return 1），deferred 里阴影消失 ⇒ 之前是实时阴影（关键字确实开着）；仍有阴影 ⇒ 那是**烘焙**阴影。

## `surface.depth` 必须是"视空间米"（已向用户证明）
- 唯一用处：`Shadows.hlsl` L455 `FadedShadowStrength(surfaceWS.depth, _ShadowDistanceFade.x, _ShadowDistanceFade.y)`，
  `FadedShadowStrength = saturate((1 - distance*scale)*fade)`，而 `_ShadowDistanceFade.x = 1f/settings.maxDistance` ⇒ **distance 必须是米**。
- 前向（`LitPass.hlsl` L81/L152）用 `-TransformWorldToView(positionWS).z`；`Fragment.hlsl` L21 的 `f.depth = positionSS.w` 也是同一个量（透视下 = 实际深度）。
- `CameraRendererPasses.hlsl` L106 `surface.depth = GTDepth`（原始深度缓冲值）是**错的**：近处 ≈0.995、远处 ≈0（反向 Z 下方向还反了）⇒ **deferred 的距离淡出等于失效**。
  修法一行：`surface.depth = -TransformWorldToView(surface.position).z;` —— **用户已自行改好**（2026-09-12）。

## 帧调试器层级怎么来的（2026-09-12，查明）
- 层级**只由 `BeginSample/EndSample` 决定**；单个绘制事件的**标签**来自 `buffer.name`（CommandBuffer 名）。
- Editor 下 `CameraRendererDeferred.Editor.cs` 的 `PrepareBuffer()` 里：`buffer.name = SampleName = camera.name`（所以最外层是**相机名**，如 "Main Camera"）。
  非 Editor 分支里 `SampleName = bufferName`，且字段初始化时 `buffer.name = bufferName`（= "Render Camera Deferred"，用户习惯去掉空格写成 `RenderCameraDeferred`）。
- `DrawVisibleGeometry()` 里 `BeginSample("GBuffer")`(L328) 一直开到光照之后(L359) → 所以中间所有东西（含我们后加的 `Screen Space Shadow`）都被套进 "GBuffer" 组里；而 `buffer.name` 在 L327 被设成 "GBuffer"、L360 才恢复成 `bufferName`
  ⇒ 这一区间录制的绘制事件都带 "GBuffer" 标签，L360 之后录制的（天空盒/透明/后处理）带 "Render Camera Deferred" 标签。**这就是用户看到的 "Render Camera Deferred" 那一层。**
- **"Deferred Lighting" 看不到的原因是代码顺序错了**：他们先 `DrawProcedural(...)` 再 `BeginSample("Deferred Lighting")/EndSample`（L355-358）→ sample 是空的，绘制落在它外面且带着 "GBuffer" 标签。
  修法：把 `DrawProcedural` 挪进 Begin/End 之间，并在它之前设 `buffer.name = "Deferred Lighting"`（顺手可把外层 GBuffer 组改名或提前关闭）。**未改，等用户决定。**

### 帧调试器层级 = 按"命令缓冲区批次"分组（2026-09-12 最终查明，重要）
**规则**：树的第一层是**每次 `context.ExecuteCommandBuffer(buffer)`（=一次 `ExecuteBuffer()`）产生的一个批次节点**，节点名 = **那一刻的 `buffer.name`**；
批次内部再由 `BeginSample/EndSample` 切出子节点。⇒ ① 想让两个东西平级，必须让它们在**不同批次**里（中间要有 `ExecuteBuffer()`）；
② 想让节点叫什么名字，要在该批次 `ExecuteBuffer()` **之前**设 `buffer.name`，**执行完再改回来**。

**用户仍看到的两个问题及成因（已给方案，用户要求先别动）**：
1. `Screen Space Shadow` 还在 `GBuffer` 大层级里：`buffer.EndSample("GBuffer")`(L346) 记录后一直没 flush，直到 `DrawScreenSpaceShadow()` 里才 flush
   ⇒ 这一批从一开始就处在"GBuffer 还开着"的状态 → 被算进 GBuffer 下。
   **修法：`EndSample("GBuffer")` 后面补一句 `ExecuteBuffer();`**
2. `Deferred Lighting` 外层多一层 "Render Camera Deferred"：L366 先把 `buffer.name` 改回 `bufferName`，L367 才 `ExecuteBuffer()` ⇒ 批次名成了 bufferName。
   **修法：把 `buffer.name = bufferName;` 挪到 `ExecuteBuffer();` 之后**，并去掉 L357 那句 RT 恢复前的 `ExecuteBuffer()`（让 RT 恢复跟光照同批次）。
- 附注：`CopyDepthAttachments`/`CopyColorAttachments` 内部各有 `ExecuteBuffer()` → 会出现几个同名的 "GBuffer" 小批次节点，这是既有行为，不必动。
- 用户已按上面两条改完，层级正确了。**新现象：`Screen Space Shadow` 与 `Deferred Lighting` 都出现"同名两层嵌套"**（层1=批次名、层2=sample 名、层3=Draw Procedural）。
  原因：**批次节点名（`buffer.name`）与 `BeginSample` 名取了同一个字符串** ⇒ 必然两层。
  建议修法（未实施）：这两批里各自只有一件事 → **只保留 `buffer.name`，删掉 `BeginSample/EndSample`**（即"想要一层就用 buffer.name 命名；`BeginSample` 只在一个批次里有多段时才用，且那时两者名字要不同）。
  **用户决定不改（2026-09-12），保持现状。**

- **用户实测：基本正确，但模糊后仍能看到噪点。** 分析（已给用户，待其决定是否实施）：
  - 我们的模糊是 5 抽头二项式、半径 ±2 纹素（σ≈1 纹素）；而泊松盘旋转是**每 2×2 屏幕像素**换一次 ⇒ 噪声波长本身就是 ~2 像素级 ⇒ σ≈1 的模糊压不住。**不是算法错，是核太窄。**
  - 建议顺序：①把核加宽到 ±3~4 纹素（σ≈2）先看噪声降不降；②加"**世界坐标距离权重**"做保边（AKG 那招：用 `_CameraDepthTexture` 重建采样点世界坐标，
    `w = 1/(1+k*|ΔworldPos|)` 或 `saturate(1-|Δ|/range)`）——便宜、不需要额外贴图/法线，能同时治"亮边漏光 + 近处硬化"；③仍嫌噪就加采样数（16+16 → 32+32/64）。
  - 蛋白胨的"compute + 深度法线图双边模糊"属于更高质量方案，等以后再上。
- **用户反驳（2026-09-12）**："我明明有法线图（`_GBuffer2`），双边不是更友好吗？" —— **用户对，我更正**：
  双边**算法**照抄蛋白胨/龙书没错，只是不必用 compute（全屏 pass 里写就行）；而且我们有 GBuffer 法线 ⇒ 法线权重只是多一次 `_GBuffer2` 采样，几乎免费。
  **结论：直接上"深度（世界坐标差）+ 法线点积"双边权重**，不要只做世界坐标权重。
- 二项式核（帕斯卡三角，归一化后）：±2 = (1,4,6,4,1)/16；**±3 = (1,6,15,20,15,6,1)/64**（正好是 AKG 说的"7×7 拆成 7+7"）；±4 = (1,8,28,56,70,56,28,8,1)/256。
  横向就是 `uv + float2(i*texelX, 0)`，i = -N..N，texelX = `_CameraBufferSize.x`（半分辨率时 ×2）。
- 概念澄清（给用户）：双边滤波**本身不要求法线** —— 它是"空间距离 + 任意一个差异度量"；图像去噪里那个度量是颜色，阴影图里换成深度。
  法线是"第二把尺子"，只在**深度接近但朝向不同**处有收益（墙角、地面与竖墙交界、坡面），否则深度一项就够。

### 已实施：blur 改成"深度+法线"双边（2026-09-12）
`ScreenSpacePCSS.shader`：
- `HLSLINCLUDE` 里新增三个共用工具：`ScreenSpaceBlurWorldPos(uv, rawDepth)`（`UNITY_MATRIX_I_VP` 重建，翻转同 DeferredLightPassFragment）、
  `ScreenSpaceBlurNormal(uv)`（读 `_GBuffer2` 解码几何法线）、`BilateralWeight(uvN, posC, normalC, depthTol)`。
- 横向/纵向两趟都换成 **±3（7 抽头）二项式 (1,6,15,20,15,6,1)/64 + 双边权重**：
  `w = kernel * saturate(1 - |ΔworldPos|/depthTol) * pow(saturate(dot(nC,nN)), 16)`，**最后除以权重和**（不是抽头数）。
  `depthTol = LinearEyeDepth(rawDepth,_ZBufferParams) * 0.05`（视深度 5%，随距离放大）；天空像素直接 return 1，邻居是天空则权重 0（防轮廓亮边）。
- `LinearEyeDepth` 在本项目可用（`Fragment.hlsl` 已在用 ✓）。
- **顺手修掉一个会编译不过的状态**：横向那趟的 `TEXTURE2D(_ScreenSpaceShadowTex);` 被人注释掉了，但它要采样这张图 ⇒ 已改回声明（纵向那趟的声明是好的）。
- 成本提示：每趟 ~21 次采样（深度 7 + 法线 7 + 阴影 7），全屏较贵 → 以后半分辨率可省 4 倍。
- 待用户实测：噪点是否消失、物体边缘是否有亮边/近处是否变软。两个可调常量：`0.05`（深度容差，调小更保边）、`pow(...,16)`（法线严格度）。

### 澄清：双边上采样 vs 漏光 vs ddx/ddy（2026-09-12）
- **双边上采样**只治"**半分辨率放大时，轮廓两侧不同表面的像素被等权插值**"造成的串色（前景边缘沾到后面物体的阴影）。
  用户看到的"不用PCSS也有的漏光"是**另一回事**：那是 shadowmap 精度/深度偏移导致的（接触处亮缝 = peter-panning，边缘斑纹 = acne）⇒ **双边上采样治不了**，用户的判断正确。
  方向：调 bias（normal/slope、`pcssNormalBias`）、加大 tileSize/调级联比例，或以后用接触阴影/SSAO 补接触处。
- **ddx/ddy（龙书/蛋白胨提到的）**：解决"大核下高物体阴影边缘的台阶"—— 要给"核横跨的横向距离"配深度偏移 `Δdepth = 核横向世界长度 × tanθ`；
  求 tanθ 的可靠办法是用 `n = normalize(cross(ddx(posWS), ddy(posWS)))`。**我们已经用几何法线算出等价的 `slope × 核半径`**（`biasBlockerWS/biasPCFWS`），所以这条**本质上已经做了**，只是法线来源不同（内插法线 vs 屏幕导数）。
  → 只有当"高物体阴影边缘还有台阶、调 `slopeBias` 也压不下去"时才值得做。
- 回答用户"两条是不是同一件事"：**不是**。ddx/ddy 那条属**画质**（大核边缘台阶）；"第3步是性能项"指把"每像素几十次采样"换成"每屏幕像素一次 + 半分辨率 + 两趟 blur"。两者只是都挂在第 3 步名下。

## forward 接入屏幕空间阴影的方案（2026-09-12，已给用户，待其实施）
**现状（已查）**：forward 有 `_CameraDepthAttachment`/`depthTextureId`，但深度纹理是在 **opaque+skybox 之后**才 `CopyAttachments` 的（软粒子用）；
**`Setup()` 里没有设 `unity_MatrixInvVP`**（deferred 设了）⇒ 重建世界坐标前必须补上。项目里**没有任何 `LightMode="DepthOnly"` pass**。
**流程（4 步）**：
1. **加一遍 depth prepass（必需）**：在画 opaque 之前，用新的 `DepthOnly` pass（只写深度 + alpha clip，**不带阴影 bias**）把 opaque 画进现有 `_CameraDepthAttachment`
   —— 复用现有深度附件 ⇒ **不需要新 RT**，正式绘制时深度测试直接命中，几乎无额外填充开销。可为省事复用 `ShadowCaster`，但它带 slope/normal bias 会把深度推歪（接收面位置不准），**建议新加干净 DepthOnly**（Lit / GPUDrivenTerrain / Unlit 各加一个，思路抄 ShadowCasterPass.hlsl）。
2. **pass0 的法线来源分叉**：deferred 读 `_GBuffer2`；forward 没有 GBuffer → 用 `n = normalize(cross(ddx(posWS), ddy(posWS)))`（这就是 ddx/ddy 真正被用上的场合）。
   用 **uniform**（如 `_ScreenSpaceShadowUseGBufferNormal`）切换，**不加关键字**。
3. **forward 渲染器接入**：Setup 补 `unity_MatrixInvVP`；分配两张半分辨率图；顺序 = depth prepass → 三趟屏幕空间 pass → opaque（`_ScreenSpaceShadowEnabled=1`）→ 天空盒 → transparent（保持1）→ 设回 0。
   三趟调用代码与 deferred 相同 ⇒ 建议抽成一个共用小工具类，两边都调。
4. **已知妥协**：透明物体采到的是"它后面不透明表面的阴影值"（URP 同款取舍）；多一遍 prepass ≈ 多一遍 shadow caster 的绘制量。
**待用户决定**：① prepass 用新 DepthOnly（推荐）还是复用 ShadowCaster；② 法线用 ddx/ddy（省一张 RT，推荐）还是再加一张深度+法线 prepass RT（URP 做法，质量更好）。

### forward 方案的用户决定 + 据此的关键简化（2026-09-12）
1. **prepass 用新加的干净 `DepthOnly`**（不复用 ShadowCaster）✓

     - **【再修正】mask 的判定方式改成"世界偏移探针"**（用户实测：拉近时半影失去渐变、出现硬台阶）：
       - 根因：原判定是"屏幕空间 4×4 子像素二值取平均 + 3 个 mask 纹素的模糊" ⇒ 半影带只有 ±12 屏幕像素；而 PCSS 真算出的半影可以宽达 `_DirectionalPCSSPenumbraMaxWorld`（世界尺寸，投影到屏幕常几十~上百像素）⇒ 渐变在带子边界被**硬裁**成台阶。镜头越近、屏幕上真实半影越宽，裁得越狠。
       - 改法：`DirectionalShadowBinaryTest` 增加 `float2 worldOffset` 重载（偏移经 `worldToUV2` **分轴**换算，保证世界空间正圆；bias 用 `(texelWorld+|offset|)*slope*SlopeBias`，与 PCSS blocker search 同口径）；mask pass 改为以纹素中心做 **3×3 世界偏移探针**，偏移量 = `_DirectionalPCSSPenumbraMaxWorld × MASK_WORLD_PROBE_SCALE`（新 define，默认 1.0 最保守）。半影不可能比它宽 ⇒ 带子自动覆盖整个可能半影，且**世界尺度**自动适配远近（近处屏幕上更宽、远处更窄）。顺带更便宜：9 次/16 屏幕像素 ≈ 0.56 次/像素（原 16/16）。

       - **第 2 步已通过用户验收**（"看起来不错，好像真的解决了"）。相对最初设想的 3 处有意偏离：① 结果图的两趟双边 blur **保留调用**（不是注释掉）——实测不调用视觉不可接受；A/B 开关 = 注释 C# 里那 5 行。② PCSS 仍是**半分辨率**（不是最初写的"全 res"，用户确认过）。③ mask 判定从"4×4 子像素"改成"3×3 世界偏移探针"（原方案半影带太窄导致硬台阶）。另有：mask 的距离补偿默认关。
       - **【已知冲突】mask 的带子宽度 = `_DirectionalPCSSPenumbraMaxWorld` = `pcss.filterTexels × pcssTexelWorld0`**（`pcssTexelWorld0 = 2*cascade0球半径/tileSize`）。用户把 pcss filter（`filterTexels`）调到 ≥10 后，地面大片变灰（mask 到处都是中间值）⇒ PCSS 又全屏跑了 ⇒ 优化失效。原因：这个值同时也是"半影能达到的最大世界宽度"（≈0.8~2.3 m @ filterTexels 10~30），地形起伏多的地方几乎每个像素都在某个阴影边界的这个距离内 ⇒ 带子自然覆盖全屏。**不是代码 bug，是"带子=最坏情况半影"这个设计与"很宽的半影设置"本身冲突**。用户观察到的"拉高 padding 能稍微缓解"正是佐证（padding 让探针变迟钝 → 少判成混合）。待定方案：给带子单独一个小的世界半径（如"cascade0 的 3~4 个纹素"），与 `filterTexels` 解耦，代价是半影最宽处的外圈会被裁（可能出现淡圈）。
       - **【精确定位：判据本身错了】** 用户澄清：症状是**广阔平地上没有阴影的地方**出现大片灰（像 peter panning 的糊影），padding 能缓解。根因不是"半影真那么宽"，而是我把**上限**当成了**实际半影**：
         `PCSSPenumbraMaxWorld` 是 cap，真实半影还要乘一个通常很小的比值 `ratio = saturate(Δ深度差 / PenumbraRef)`（shader 里 `PCSSDirectionalShadow` 就是这么算的）。举例：sphereR0=20 m、tile=512 → 1 纹素≈0.078 m；`filterTexels=20` → 探针半径 1.56 m，而 1 m 高物体在 45° 光下的真实半影只有约 4~8 cm（ratio≈0.03~0.05）⇒ **带子比真实半影宽 20~40 倍** ⇒ 只要附近有东西（哪怕它的影子根本不在这个像素上）就被判成"半影"⇒ mask 大片灰、PCSS 全屏白跑。padding 缓解 = 让探针变迟钝，正好反证判据错。
         **正确判据**：带子 ⟺ 本地半影宽度在屏幕上比 ~1 个像素粗。本地半影 = `saturate(Δ/PenumbraRef) × PenumbraMaxWorld`，Δ 来自"迷你 blocker search"（几次点采样取被遮挡样本的平均深度）；屏幕尺度用 `ddx/ddy(worldPos)`（≈worldPerPixel）拿。这样：平地+硬阴影（Δ小）→ 直接二值 0/1（和 PCSS 视觉等价，因为半影本来就细于一个像素）；宽半影（Δ大）→ 才标带子（不会被硬裁）。
       - **【最终实现】mask 判定 = `Shadows.hlsl::EstimateShadowBandValue()`（三步，返回 0/1/0.5）**：
         ① 迷你 blocker search（3×3，半径 `_DirectionalPCSSSearchRadius`、bias 与 PCSS blocker search 完全同口径）→ 一处遮挡都没有 ⇒ 返回 1；
         ② `penumbraWorld = saturate(Δ/PenumbraRef) × PenumbraMaxWorld`；细于 `MASK_BAND_MIN_TEXELS`(0.5) × `worldPerMaskTexel` 就返回中心的二值（bias 用"紧"的那套：padding + 2纹素坡度）；
         ③ 拿 `penumbraWorld` 当半径再做一圈 3×3 边界探测（中心和邻居比明暗，两边同一套 bias ⇒ 系统偏差抵消）：全一致 ⇒ 返回中心二值；有不一致 ⇒ 返回 0.5（带子）。
         **第③步是必需的**：只有②的话，阴影**内部**也会被标成带子（PCSS 的半影公式在内部也很大）⇒ 又白跑。③把内部（全一致）排除掉了。
         `MASK_BAND_MIN_TEXELS` 定义在 **Shadows.hlsl**（不能定义在 shader 的 HLSLINCLUDE：include 在 define 之前，且 Terrain 等共享该头文件）。`MASK_BLUR_RADIUS` 曾降到 1，**用户要求按 akg 原文改回 3**（±3=7抽头）：带子宽度虽由判据决定，但 ±3 能把带子边界的1/4分辨率块状感抹平、并给外圈留更宽的保守余量（代价是 PCSS 覆盖面变宽一点）。mask 的 ddx 要在所有提前 return **之前**算（ddx 是象限级的，有 lane 提前返回会把同象限其它 lane 的导数带歪）。
         **死码清理**：`Shadows.hlsl::DirectionalShadowBinaryTest`（旧的世界偏移单点二值判定）**已删除**（零调用者，被 `EstimateShadowBandValue` 取代）。剩余待定：`ScreenSpacePCSS.shader` 的 `#pragma multi_compile _ _RECEIVE_SHADOWS`（控制的早退已注释，白翻倍变体）、`CameraRendererDeferred.DrawGBuffers()`（调用处被注释）；保留不动的有：距离补偿那两段（可随时开的开关）+ 两趟双边 blur。
     - **两个已确认的设计决策**：① `_ScreenSpaceShadowTex` 保持**半分辨率**是可以的（akg 的"全分辨率"指的是他的 PCSS 直接算在屏幕像素上；本项目这张结果是独立 R8 图、光照 Pass 用 linear 采样上采样）——只有两个注意点：PCSS pass 里采 mask 必须用 linear，且半分辨率下"半影带"的纹素宽度只有 1/4 图的 0.5 倍，mask blur 半径别太小。② **mask 的模糊不要用双边**：目的从"给全屏 PCSS 去噪"变成"把半影带扩宽"，而深度/法线权重恰好会抑制"跨物体边界"的扩散（阴影边界就在物体接触处）→ 帮倒忙；且双边每抽头 3 次采样、纯箱式每抽头 1 次采样，这是省下的大头。
