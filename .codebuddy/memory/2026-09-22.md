## 🆕 GI 方向定案：**做 SSGI**（不选 RSM）

- 用户原话大意：RSM"不太主流"，直接做 SSGI；并问"除了运动矢量还缺什么依赖""比较厉害的实现是 SSGI 和其他混合，你怎么看"。
- **给用户的依赖分析（结论）**：
  1. **"命中点着色"是关键缺口**：不能直接拿命中像素的颜色（那里已经是它的直接光+间接光 ⇒ 过亮/二次弹射）。
     正确做法 = 取命中点的 **albedo(GBuffer1) + emissive(GBuffer4) + 法线**，再乘一个"廉价直接光（主光 · N · 一次阴影采样）"。
     ⇒ **SSGI 只能做延迟**（前向没有 albedo 快照；也符合项目"屏幕空间效果只做延迟"的既定定位）。
  2. **自己的降噪链**：半分辨率 + 持久历史（时间累积）——结构照 SSR（有先例 ✓）；TAA 已有 ✓。
  3. **随机源**：每像素 1~4 条半球射线，方向用低差异/蓝噪声；可借 TAA 的 Halton 序列。
  4. **可信度回退 = 混合**：出屏/未命中 ⇒ 回退 **SH 光照探针**（`SampleLightProbe` ✓ 已有）⇒ 这就是"混合"，几乎零成本
     （结构同 SSR 的 `alphaCalc`：可信度 a ⇒ 回退环境反射 / 这里 ⇒ 回退 SH）。
  5. 可选：SSAO/GTAO 补近处接触阴影（现在没有 SSAO，非必需）。
  6. 运动矢量：相机移动我们的重投影能覆盖；**只有物体移动时**才有拖影（GI 低频，拖影会明显）。
- **混合方案的看法（已答）**：主流确实是"屏幕空间 + 离屏兜底"（UE5 Lumen = 屏幕追踪 + 距离场/体素 + 探针；Godot = SDFGI + 屏幕追踪）。
  对我们最实际 = **SSGI + 已有 SH 探针兜底**；以后要升级是把"兜底"从 SH 换成 **DDGI 探针**，上层结构不用动。
  ⇒ 结论：**先做"SSGI + SH 兜底"，别一上来搞 DDGI。**

- **我们自己的简化（为了快 + 没有 MV）**：① **不做自建时间累积**（CGBull 用 MV 做的 Temporal 那步跳过）⇒ 只做空间双边滤波 + **交给已有 TAA 去噪**；

## 📄 CGBull 源码（`C:\Users\86156\Desktop\ssgi\cgbull代码\`，三个文件）已读，结构如下

- `ScreenSpaceIndirectDiffuse.cs`（**MonoBehaviour + CommandBuffer**，built-in 管线）：挂在相机上，CB 插到 `CameraEvent.BeforeImageEffectsOpaque`；
  8 张 RT（Hi-Z 主图 RHalf+手动逐级 CopyTexture、Hi-Z 落地备份图、**SceneColor 拷贝**、TraceMask(ARGBHalf，按分辨率全/半)、TemporalPrev/Curr、Bilateral、CombineScene）；
  每帧：拷深度 → 逐级 Hi-Z → 拷 SceneColor → Pass1 追踪 → Pass2 时间累积 → Pass3/4 双边 → Pass5 合成到屏幕（Pass6 只输出间接光当调试）。
  参数：分辨率(全/半)、RayNums(1~16)、Thickness、ScreenFade、RaySteps、HiZ max/start/stop level、**蓝噪声贴图**、GI 强度、TemporalWeight/Scale、Denoise 开关。
- `ScreenSpaceGlobalillumination.shader`：7 个 pass 壳（0=Hi-Z 生成 1=追踪 2=时间 3/4=双边X/Y 5=合成 6=调试图）。
- `SSGiPass.cginc`（全部逻辑）：
  - Pass1 追踪：深度重建 pos/viewdir + GBuffer1.a 当粗糙度、GBuffer2 当世界法线 → **蓝噪声** 采样 → **concentric disk + sqrt(1-r²) = cosine 半球** →
    屏幕空间射线 + Hi-Z 步进 → 命中后 **采 `_SSGi_SceneColor_RT`（场景最终颜色，= 二次弹射的坑）** + 命中点法线算
    `Occlusion = 1 - saturate(dot(World_L, hitNormal))` → `* rcp(1+Lum)` **压缩** → 多条平均 → `* rcp(1-Lum)` **还原** → 输出 `(颜色*mask, EyeDepth)`（**深度塞 alpha**，供双边用）。
  - Pass2 时间：`ResolverAABB`（邻域 min/max + 方差）→ 历史用 **MV** 取、clamp 进 AABB；权重 `saturate(TemporalWeight*(1-length(Velocity)*2))`；**没有深度/法线一致性检查**。
  - Pass3/4 双边：半径 12，权重 = 高斯 × 深度差（`_ProjectionParams.z` 缩放）；**只用法线深度、没有法线权重**（他自己也说会糊）。
  - Pass5 合成：`DeferredLighting = SceneColor - ReflectionColor`；`DirectIrradiance = DeferredLighting / BaseColor`（反除 albedo 还原辐照度）；
    最终 = `IndirectIrradiance * BaseColor + DeferredLighting + ReflectionColor`（= 在原图上加一层间接光，并去掉原环境/反射的重复）。
- **C# 全流程（讲给用户听过）**：`[ExecuteInEditMode]` 挂相机；`Awake` 建材质 + CB；`OnEnable` 把 CB 插到 `CameraEvent.BeforeImageEffectsOpaque`；
  `OnPreRender` = Halton 随机种子 + `SSR_UpdateVariable()`（**尺寸变了才重建 8 张 RT**、每帧设 7 个矩阵 + uniform）+ `RenderScreenSpaceIndirectDiffuse()`（录命令）；
  `OnDisable/OnDestroy` 移除 CB + 释放。
  - ⚠️ 它用 `RenderTexture.GetTemporary/ReleaseTemporary` 靠"尺寸没变就不重建"来跨帧保留 ⇒ **有隐患**（我们已踩过：跨帧数据必须用**持久 RT**）。
  - 每帧命令：拷 ResolvedDepth →（循环 i=1..maxLevel：pass0 算到 BackUp 的 mip i → `CopyTexture` 到主图 mip i）→ `CopyTexture(CameraTarget → SceneColor)` →
    pass1 追踪 →（Denoise：pass2 时间 → CopyTexture 换历史 → pass3 横 → pass4 纵，**每趟后都 CopyTexture 回 Prev 倒手 = 3 次全分辨率拷贝**）→
    pass5 合成到 CameraTarget（或 pass6 只输出间接光）→ 帧末更新 `_Prev_ViewProjectionMatrix`。
  - **移植映射**：`CameraEvent` → 我们渲染器的 `Setup/Draw/Cleanup`；`ResolvedDepth/CameraTarget` → 我们的附件 id；
    `GetTemporary` → **持久 RT**；`_CameraGBufferTexture0~2` → 我们的 `_GBuffer1/2/4`；`_CameraReflectionsTexture` → 我们的环境反射路径。
- **我们要改的点（和之前结论一致）**：① 命中点改用 GBuffer albedo/emissive+主光近似（他采最终颜色 ⇒ 二次弹射）；
  ② 双边加**法线权重**；③ 时间累积第一版**交给 TAA**（他的依赖 MV）；④ 没命中 → **回退 SH 探针**（他没做 fallback，屏幕外是黑的）；
  ⑤ Hi-Z 我们已有（`HierarchicalZ`）；⑥ 他 6 趟 + 每趟 CopyTexture，我们可以合并/减少。
- ⚠️ **更正一处我之前说错的地方（2026-09-22）**：CGBull 的 Hi-Z 生成用"算到 BackUp 图（`SetRenderTarget(BackUp, mip=i)`）再 `CopyTexture` 进主图 mip i"**不是浪费、也不能省** ——
  同一张图不能同时当"纹理读"和"渲染目标写"（D3D 上会读到 0，**我们 `HierarchicalZ.Draw` 的注释里就写着"实测过"**），
  而**我们的实现是同款**：每级借一张单级临时图（`GetTemporaryRT`）算完 → `CopyTexture` 进主图对应 mip，**主图全程不当渲染目标**。
  差别只是形式：它用"一张带 mip 的备份图 + SetRenderTarget 指定 mip"，我们用"每级一张单级临时图"⇒ 等价，不存在"我们更省"。
  ⇒ **Hi-Z 生成这块我们和它成本相同**，直接复用我们的 `HierarchicalZ` 即可。
- **`TraceMask_RT` 是什么（用户问过）**：它就是**追踪那趟的输出图**（ARGBHalf，全/半分辨率），
  `rgb = GI × 可信度mask`、**`a = 眼空间深度`**（深度塞 alpha 给后面的双边当权重）。"mask" = **命中率 + 屏幕边缘淡出**的置信度
  （`Square(RayHitData.a * GetScreenFadeBord(...))` 的平均，`saturate(mask*2)` 压暗 GI），
  用途：① 屏幕边缘/命中少的像素 GI 变弱 ② 就是他文章里说的 `SSMask`（以后 `lerp(SSGi, ProbeGi, SSMask)` 和探针 GI 混合）。
  ⇒ **它不是"限制计算范围的遮罩"，也不是额外的纹理**（它就是那张 GI 图本身）。
  ⑦ 可抄的技巧：`(颜色*mask, EyeDepth)` 打包、**`rcp(1+Lum)` 压缩 / `rcp(1-Lum)` 还原**（和我们 TAA 的夹心同款）、concentric disk 半球采样、反除 albedo 的合成思路。

## 💡 澄清（2026-09-22 答用户 5 问，值得记住的几个点）

- **半球采样 ≈ SSAO 同款**：都是"像素半球里打若干方向、判遮挡"；SSAO 只统计"挡了多少"（黑白），SSGI 把"撞到的颜色"也带回来（有色）。**SSAO = SSGI 只取遮挡项的那一半。**
- **为什么命中点不能采"最终颜色"**：最终颜色 = 它的直接光 + 间接光 + 环境都在里面 ⇒ 拿它当"从命中点射出的光"就等于**把间接光算了两遍**（且含我们还没加的环境/反射，能量对不上、还会随 TAA 累积漂移）。
  正解 = 命中点的**出射辐照度** = `albedo × 到达该点的直接光`（+ 该点 emissive）。执烛的 "Copy Direct Lighting（单独缓存一张只有直接光的图，命中点采它）" = **同一思路的另一种实现**（更准、含所有光源，但多一张全分辨率图）。
- **CGBull Pass1 里的 `1 - saturate(dot(World_L, 命中点法线))`**：便宜的"朝向惩罚/背面惩罚"——本质是在**代替执烛的 Backface Depth**（真背面剔除），所以"便宜但要小心"（掠射/背面附近的命中会被压暗）。
- **CGBull Pass5 里的 `DirectIrradiance = DeferredLighting / BaseColor` 是死变量**（算了没用，最后那行只用了 `IndirectIrradiance`）。
  `SceneColor - ReflectionColor` 的思路 = "把原图里的环境/反射剔除，再按辐照度层面加新的间接光"，目的是**避免环境光重复叠加**（我们管线在物体着色时 `gi.diffuse` 就混好，所以不需要这种减法）。
- **删减后的执烛 vs CGBull**：主干一一对应（RayMarch / Temporal / 双边 / Combine），三处明显不同 = ① 命中点着色（执烛有直接光图，CGBull 采最终颜色）② 降噪层数（执烛 3~4 层含 ReBLUR，CGBull 只有时间 + 一层深度双边）③ 半分辨率上采样（执烛有深度法线引导，CGBull 是简单 blit）。
  另外执烛追踪是"世界空间自适应步长 + 二分"，CGBull 是"屏幕空间 Hi-Z 步进"——**Hi-Z 我们已经有了，这块我们比 CGBull 强**。

## 🔧 澄清（2026-09-22 用户确认理解时问的 3 点）

- **`TraceMask`** = 本帧**追踪出来的间接光**（`rgb = GI×可信度`、`a = 眼空间深度`）⇒ 它是 **Pass2 时间累积的"当前帧输入"**（Pass2 读 `_SSGi_RayCastRT` = TraceMask，和历史混合后写 `TemporalCurr`）；关掉降噪时它直接拷/blit 到 `Bilateral` 再被合成用。
- **`TemporalCurr`** = **时间累积后的"间接光"**（不是场景最终颜色，也只在开降噪时存在）。
- **`CombineScene`** = "原图 + 新间接光"**合成后的最终画面**（先写它，再 blit 到屏幕）⇒ 和 `TemporalCurr`（间接光）是两回事；合成那步真正读的 GI 图是 `Bilateral`（滤波结果）。
- **我们移植时的对应关系（最终结论，不是"后面都照他的来"）**：
  | CGBull | 我们 |
  |---|---|
  | 1 拷深度 / 2 逐级 Hi-Z / 3 拷 SceneColor | **全不要**（Hi-Z 用现成 `hiz.Draw`；SceneColor 不采） |
  | 4 Pass1 追踪 | **要**，但命中点着色改 GBuffer(albedo/emission)+主光；未命中回退 SH |
  | 5 Pass2 时间累积 | **第一版不要**（交给 TAA） |
  | 5 Pass3/4 双边 | **要**，加**法线权重**；横竖两趟用**一张临时倒手图**（照 SSR） |
  | 6 Pass5 合成 | **不要**（改成物体着色时加到 `gi.diffuse`） |
  | 7 帧末更新上一帧 VP | **不要**（没时间累积就用不上） |
  ⇒ 最终 = **2 张持久半分辨率 GI 图（双缓冲）+ 1 张临时半分辨率倒手图**；流程 = Trace 写临时图A → BlurX → 临时图B（或直接换向）→ BlurY **直接写进持久图的 write 那张**（省一次拷贝）⇒ 帧末换索引。

## 📋 我们的 SSGI 最终流程（2026-09-22 定稿，讲给用户听过）

- **资源（就这些）**：2 张**持久**半分辨率 GI 图（双缓冲）+ 2 张**半分辨率临时**倒手图；其余全复用（Hi-Z / 深度 / GBuffer / 阴影 / SH 探针 / IGN / TAA）。
  - **省一张图的关键**：双缓冲里"read 那张"既是**物体着色要读的上帧结果**，又是 **Temporal 的历史**（等同 CGBull 里"Prev 到最后存的是滤波结果"）。
  - ⚠️ 副作用：历史是"滤波后"的结果 ⇒ 相当于滤波两次（偏糊）；以后可改成"历史只存时间累积（滤波前）"当优化。
- **`TraceMask` 不需要单独的贴图**：它**就是追踪那趟的输出图**（`rgb = GI×可信度`、`a = 眼空间深度`）；在我们这儿 = 半分辨率临时图 A。
  深度塞进 alpha 只是打包技巧 ⇒ **也不需要单独的深度图**供滤波用。
- **帧内顺序（定稿）**：
  1. `Setup`：判定 use（enabled + shader + 延迟 + 非反射/预览相机）→ 按需建两张持久图 → `_SSGITex` 绑成 **read 那张** → 存 `currentViewProjection`（未抖动）→ 传参。
  2. 物体着色（GBuffer pass）：`gi.diffuse = lerp(烘焙(SH/光照贴图), _SSGITex.rgb * 强度, _SSGITex.a)`（a=0 ⇒ 自动退回烘焙）。
  3. `hiz.Draw(buffer)`（已有）。
  4. **Trace 趟**（半分辨率→临时图 A）：深度重建位置+法线 → IGN 生成 cosine 半球方向 → Hi-Z 步进 → 命中采 GBuffer1(albedo)+GBuffer4(emission) 乘"主光 N·L×阴影"、
     + `1-dot(方向,命中点法线)` 朝向惩罚；未命中/出屏 ⇒ `SampleLightProbe` SH 兜底；输出 `(GI×可信度, 眼深度)`。
  5. **Temporal 趟**（→临时图 B）：深度 + `_SSGIPrevViewProj` 重投影（同 TAA 那套；**不做抖动处理**，追踪本就用像素中心）→ 3×3 AABB 截断历史 → `lerp`，权重随运动减小；首帧/reset ⇒ 直接用当前帧。
  6. **BlurX**（读 B 写 A）：双边（深度 + **法线**权重）。
  7. **BlurY**（读 A 写 **持久图的 write 那张**）：同上，省一次拷贝。
  8. 帧末：`previousViewProjection = currentViewProjection`；换双缓冲索引。
  9. `Cleanup`：还两张临时图。`Dispose`：释放两张持久图 + 材质。
- 前向渲染器：只把 `_SSGITex` 绑成 1×1 黑（a=0 ⇒ 退回烘焙），不做 SSGI。
- **第一版唯一砍掉的 = Motion Vector**（Temporal 用深度重投影代替；代价 = 动的物体拖影）。

### 🔬 第一次实测后的观察 + 诊断（2026-09-22，用户反馈）

用户观察：① 有全局光照感（墙上有邻近物体的颜色）但**弱/不明显**；② 有**明显漏光**（不该亮的地方在亮，"像是 SSGI 没算这里、让默认环境光接管"）；
③ `thickness` 得调到 **2** 才有更多间接光；④ `rayCount` 1 和 16 看不出差别。

诊断（我给的结论）：
- **③ 是关键线索**：厚度调大才有 GI ⇒ 大量射线在"该命中"时被判成**没命中（穿透）**。默认 `thickness = 0.05` 米太薄
  （SSR 那边默认 `pixelThickness = 0.15`）⇒ 先把它调到 **≈0.15**。
- **② 漏光的直接来源 = "未命中就塞一个 SH 探针的亮值"**：SH 是整半球平均、不知道局部遮挡 ⇒ 缝隙/角落/出屏处被填亮。
  改法：**未命中只降可信度 a、不往 rgb 里塞 SH**（消费端 `lerp(烘焙, GI, a)` 会自然退回烘焙，不会凭空变亮）。这比"per-ray SH 填充"更不容易漏光。
- **"该暗的地方亮"的另一半 = 完全没有 AO**：我们只做"加"，没有任何东西压掉角落/缝隙里的烘焙环境光 ⇒ 需要 SSAO/GTAO，
  或退一步用"追踪命中率"当 AO 去压 baked。这是"GI 感弱 + 漏光"两个症状的共同结构性缺口。
- **④ 用户猜对了**：时间累积（历史权重 0.9）+ 两趟 25 抽头双边把每帧噪声抹平了 ⇒ 射线数只影响收敛速度/残留质感。
  想看出差别：`blurRadius` 降到 2~4、`temporalWeight` 降到 ~0.5。
- **① GI 弱的一个技术原因**：我们把它当**替换**用（`lerp(烘焙, GI, a)`），而命中点只算主光一次弹射 ⇒ 系统性比 SH/光照贴图暗，
  换上去反而变暗、渗色被摊薄。短期：`intensity` 试 2~4，或改成"在烘焙之上叠加"。

### 🔍 研究（2026-09-22）：怎么加"其他光源"（点光/聚光）参与命中点着色 —— 结论 + 待用户拍板

- **C# 侧一行都不用改**：`Light.hlsl` 的 `_CustomLight` CBUFFER 里 `_OtherLightCount` + `_OtherLightColors/Positions/DirectionsAndMasks/SpotAngles/ShadowData`
  （最多 64 盏）都是**全局**上传的，而我们的 shader 经 `CameraRendererPasses.hlsl` 已经 include 了 `Light.hlsl` ✓。
- 着色写法（和主光那项同口径、直接相加）：命中点循环
  `if (distSqr * _OtherLightPositions[i].w >= 1) continue;`（超出灯的范围，几次 ALU 早退）→
  `Light l = GetOtherLight(i, hit, shadowData);` → `irradiance += l.color * saturate(dot(hitNormalWS, l.direction)) * l.attenuation;`
  （`attenuation` 自带 range/spot 衰减 + `/distanceSqr`）。
- ⚠️⚠️ **顺手发现一个疑似 bug**：`Shadows.hlsl` 的 `GetDirectionalShadowAttenuation` / `GetOtherShadowAttenuation` 开头都是
  `#if !defined(_RECEIVE_SHADOWS) return 1.0;`，而 **SSGI 的 shader 没声明 `_RECEIVE_SHADOWS`** ⇒ 命中点的主光阴影**很可能完全不生效**
  （阴影里的命中点被当成亮的 ⇒ 又一处漏光来源）。修法：给 SSGI 的 pass 加 `#pragma multi_compile _ _RECEIVE_SHADOWS`（2 个变体，代价很小）。
  另外我们**没**声明 `_SHADOW_PCF3/5/7`、`_DIRECTIONAL_PCSS` ⇒ 走的是最便宜的硬件 PCF2x2、也不会误入昂贵的 PCSS ✓（这点是好事，要保持）。
- 成本：每根射线 × 每次命中 × N 盏灯；(64 盏全扫一遍距离) 也不便宜 ⇒ 需要 `otherLightLimit` 设置（0 = 关，默认建议 2）。
- 其他光**阴影**：`GetOtherLight` 会采 `_OtherShadowAtlas`；但受同一个 `_RECEIVE_SHADOWS` 门控 ⇒ 不加关键字就**免费且无阴影**（第一版就这样，用户待定）。
- 渲染层过滤：命中点的层掩码可从 `_GBuffer3.a` 解出（项目已这么存），配 `RenderingLayersOverlap(hit, light)`；
  ⚠️ 但**延迟光照 pass 里这两个检查现在是注释掉的**（`GetLightingDeferred`）⇒ 加了会"GI 比直接光更严格"，建议先不加。
- **待用户拍板**：① 上限默认几盏；② "前 N 盏 + 距离早退"（最省）还是"取最近 N 盏"（多一遍 64 次距离扫描，更准）；
  ③ 要不要顺手加 `_RECEIVE_SHADOWS`（修主光阴影）；④ 渲染层过滤先不加？⑤ 其他光阴影第一版不做？

**→ 用户已拍板（2026-09-22）**：
- 设置项 `otherLightLimit`：`[Range(0, 8)]`，**默认 2**（0 = 关）。
- **② 改成"取最近的 N 盏"**（用户推翻我的"前 N 盏"建议："肯定不会去用没准在哪的灯去算啊"）。
  实现要点：先扫全部 `_OtherLightCount`（最多 64，只算 `distSqr`），维护一个**固定 8 槽**的"最近 8 盏"（槽位是编译期常量、纯寄存器，别用动态索引的局部数组 —— 会 spill 到 local memory），
  再按 `otherLightLimit` 取前几槽调 `GetOtherLight`。代价 ≈ 64×8 次比较（纯 ALU，比一次纹理采样便宜）。
- **加 `_RECEIVE_SHADOWS`**（只加在 **Trace 那个 pass** 的 HLSLPROGRAM 里就够 —— 只有它调 `GetShadowData`/`GetDirectionalLight`；变体 ×2）。
- **不加** `_SHADOW_PCF3/5/7`（保持最便宜的硬件 PCF2x2）；**不加** `_DIRECTIONAL_PCSS`（会让命中点阴影走 PCSS ⇒ 每根射线几十次采样，而且跑的时候 `_ScreenSpaceShadowEnabled = 0`，走不到屏幕空间那条路、纯白算）。
  **回答用户的疑问（"阴影图不是早就算好了吗，为什么加档位会贵"）**：贵不在"渲染阴影图"（那是每帧一次、和 SSGI 无关），而在**每次阴影采样要走多少纹素**：
  PCF2x2 = 1 次 fetch、PCF3x3 = 9、PCF5x5 = 25、PCF7x7 = 49、PCSS = 32(blocker)+32(采样) ≈ 64。

- 渲染层过滤**先不加**（与延迟光照 pass 现状一致）。
- **其他光的阴影跟"阴影那一步"一起做**（加了 `_RECEIVE_SHADOWS` 后，`GetOtherLight` 内部的 `_OtherShadowAtlas` 采样自动生效；数据 C# 早就上传了）。
- **实施顺序：① 先加 `_RECEIVE_SHADOWS`（主光+其他光阴影同时生效）→ ② 再加其他光循环**（那时其他光阴影自动带上）。
  用户原话："我预计是其他光改一次 + 阴影改一次"（顺序建议反过来：阴影在前）。

### 🔧 更正 + 落实（2026-09-22，用户对"不加 PCF/PCSS"存疑，我重新查了机制）

- **关键字机制（已核实代码）**：
  ① **不带 `_local` 后缀的关键字其实是"全局关键字"** ⇒ `_RECEIVE_SHADOWS` 是被**对象材质上的 `_ReceiveShadows` 开关**（Unity 的 `Material.EnableKeyword` 对非 local 关键字等于全局打开）**全局打开**的 ——
     这正是 `CameraRenderer.shader` 用 `multi_compile` 而不是 `shader_feature` 的原因（它的注释写的就是这个）。
  ② **但 shader 必须自己声明才能"看见"它**：我们的 SSGI pass 没声明 ⇒ `GetDirectionalShadowAttenuation/GetOtherShadowAttenuation` 开头的
     `#if !defined(_RECEIVE_SHADOWS) return 1.0;` 恒成立 ⇒ **命中点现在没有任何阴影**（这条结论成立）。
  ③ `_SHADOW_PCF3/5/7` 与 `_DIRECTIONAL_PCSS` 由 `Shadows.cs` 的 `SetKeywords()` 用 **`buffer.EnableShaderKeyword/DisableShaderKeyword`（全局）** 每帧设置 ✓（已读到代码）。
- **两种等价修法**：(a) 在 **Trace 那个 HLSLPROGRAM** 里加 `#pragma multi_compile _ _RECEIVE_SHADOWS`（2 个变体、无额外采样；
  同时让主光**和其他光**阴影生效 —— 其他光阴影在 `GetOtherLight` 内部，也受同一个门控）；
  (b) 照 `ScreenSpacePCSS.shader` 的做法**绕开关键字**（`GetShadowData` + `GetDirectionalShadowData` + **`GetCascadedShadow`**，那个函数不带门控）——
  但那样只解决主光，其他光阴影得自己抄一份。**我倾向 (a)**。
- **PCF 档位 / PCSS 的结论不变，但理由更准确**：声明它们才会**跟随资产里的档位**（当前 filter 设置）；
  不声明 = 编译期固定走**硬件 PCF2x2**（最便宜）。这是**我们主动选**（不是被门死）：查询次数 ≈ 9 次/像素（射线×命中×灯）·
  vs 光照 pass 的 1 次 ⇒ PCF7(49 fetch)/PCSS(≈64 fetch) 会被放大 9 倍；且 GI 低频、软硬看不出。⇒ **不声明**。
- **回答用户"全屏 pass 没有物体，怎么取每个物体最近的点光"**：选灯是相对**命中点的世界坐标**（不是物体）——
  每个像素每根射线命中点本来就重建了世界坐标（算 N·L 用的就是它）⇒ 按"命中点到各灯的距离"挑最近 N 盏即可，粒度比"每物体"还细。

### 追加澄清（2026-09-22 第二轮问答，用户看到"GI 位置不自然 / 暗处有天空盒亮")

- **为什么"替换 + 一次弹射"会比 SH/光照贴图暗**：烘焙那张图含**所有**来源（太阳 + 天空/环境 + 其他灯 + 多次弹射近似），
  而我们的命中点只有 `主光 × N·L × 阴影`（阴影里的命中点直接是 0），**完全没算天空/环境那一大项**
  ⇒ 拿它替换烘焙，画面必然偏暗。这也解释了"GI 感弱"。
- **"阴暗位置的 lit 物体上有很亮的环境/天空盒高光" ≠ SSGI 的锅**：SSGI 只动 `gi.diffuse`，
  `gi.specular` 还是 `SampleEnvironment`（没反射探针时 `unity_SpecCube0` = 默认天空盒）⇒ 那是**环境反射**的老问题（和 SSR 那条路同源）。
  判别方法：**临时关掉 SSGI（或勾 debugIndirect）**——亮还在就不是 SSGI；若亮是"漫反射整体偏亮"，那是 baked(SH/光照贴图) 未被 AO 压，
  属于"没有 AO"那条（P0-③）。
- **"GI 出现在不该在的位置/形状不自然"**：半分辨率 + 大半径双边（12 GI texel = 24 屏幕像素）把 GI 摊成糊块并串色；
  穿透（厚度）、无背面剔除、无 AO、只有 3 条射线 + IGN 的方向成片偏好、动的物体靠重投影（无 MV）都会加剧。
- 用户确认：`intensity` 拉大后 GI 表现明显 ✓；blur 前的图里射线数差别很大（只是被后的去噪抹平）✓。
