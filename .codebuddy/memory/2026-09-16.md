   `decodeInstructions = unity_SpecCube0_HDR` ⇒ **`.x`（曝光/强度）= 0 ⇒ 整个返回 0** ⇒ env 采样恒为黑。
5. 于是 `CompositePassFragment` 里 `giSpecular = SampleEnvironment(surfaceWS, brdf, uv)` = `lerp(黑, ssr.rgb, a)`：
   - SSR **命中**的像素（a>0）还有内容（所以看起来"SSR 在工作"）；
   - **未命中**的像素（a=0）本该退回环境反射，结果退回**黑** ⇒ 即"环境高光整块丢失"、画面偏暗。

**一行验证方法（给用户的）**：在 `CompositePassFragment` 里临时 `return float4(unity_SpecCube0_HDR.xyz, 1);`（应全黑）或 `return float4(SampleEnvironment(surfaceWS, brdf), 1);`（应黑）；同一个 shader 在 `LitPassFragmentGBuffer`（逐物体）里输出同样的东西应当是亮的。

**修法（未动笔，等用户拍板）**
- **A（推荐）**：合成 pass 不读 `unity_SpecCube0*`，改读 C# 每帧上传的"相机默认环境"：`ReflectionProbe.defaultTexture` + `ReflectionProbe.defaultTextureHDRDecodeValues` → 新全局 `_DeferredEnvCube`(TEXTURECUBE) / `_DeferredEnvCubeHDR`(float4)。取舍：全屏 pass 拿不到"每像素属于哪个探针" ⇒ 只能用场景默认环境（默认探针/天空盒）；有探针体积的场景偏差可见。
- **B（最省、近似）**：合成 pass 不算 env —— GT4 恢复写"env 高光"（`_UseScreenSpaceReflectionInDeferred > 0` 时也写 `IndirectSpecular(env)`，因为**GBuffer 阶段的逐物体探针是对的**），合成 pass 只加 `IndirectSpecular(surface, brdf, ssr.rgb * _SSRIntensity) * saturate(a)`。代价：命中处会多算一份 `a * env`（略亮）。优点：零新 uniform、探针正确。
- **C（不建议现在）**：HDRP 式"专门的环境 pass / probe atlas"，成本大。
- 进阶（既不丢探针又精确）：让 GBuffer 阶段用**上一帧** `_SSRTex.a` 把 env 高光加权 `(1-a)` 写进 GT4，合成 pass 只加 `a*ssr`；代价是多一帧时域耦合 + 首帧无数据。

**影响范围**：**只影响延迟**的合成 pass。前向的 env 是在材质里逐物体算的 ⇒ 正确。

### 追加问答（2026-09-16）：合成 pass 想"读到环境高光"，有哪些可行做法

用户问"难道真的没能在合成 pass 里采样环境高光的做法吗"。答案：**有，但都不是"直接读 `unity_SpecCube0`"**。补充的关键事实：
- 不可靠的不只是 `unity_SpecCube0_HDR`（在 `UnityPerDraw`），**逐物体的那一整套探针参数**（`unity_SpecCube0_BoxMin/Max/ProbePosition/HDR`）在合成长 pass 里**全都不可靠**；本项目目前也没做 box projection（`SampleEnvironment` 就是普通 cube 采样 + HDR 解码）⇒ 缺的只是"哪张 cube + 解码参数"。
- 可行菜单：
  - **(a) C# 喂全局默认环境**（`ReflectionProbe.defaultTexture` + `defaultTextureHDRDecodeValues`）：合成 pass 里能真采 env，代价 = **只有场景默认探针/天空盒**，丢逐物体探针。
  - **(b) 单独一张 GBuffer 存 `IndirectSpecular(env)`**（GBuffer 阶段逐物体算、探针对）：合成 pass 读它 ⇒ 能做数学精确的 `env*(1-a) + a*ssr`。代价 = **多一张 MRT/更多带宽**（`GT4` 是 R11G11B10，打包了 emission+漫反射+env高光，拆不出来）。
  - **(c) 不在合成里采 env**：GBuffer 阶段用**上一帧**的 `_SSRTex.a` 先把 `(1-a_prev)` 乘进 env 高光再写 GT4，合成 pass 只加 `a*ssr` ⇒ 精确、不采 cubemap，代价 = 权重滞后一帧 + 首帧无数据。
  - **(d) 自建探针 atlas + 逐像素探针索引**（HDRP 路线）：正确但工程量大。
  - 现状（env 在 GT4 + 合成只加 `a*ssr`）就是"不做任何 env 采样"的最省版，代价是命中处略亮。
  ⇒ 结论：**想在合成 pass 里精确做替换，最省的是 (a)（丢逐物体探针）或 (c)（滞后一帧）；要逐物体探针又精确就得 (b)/(d)。**

### 用户改主意（2026-09-16）：改选 **(b) 多加一张 GBuffer 存"间接高光的环境采样"**

即：**延迟 + 开 SSR 时，多一张 GBuffer（暂称 GT5）写 `IndirectSpecular(env)`**，合成 pass 读它 ⇒ 精确版，且合成 pass 仍然**不采 cubemap**。

**精确数学（已推导，给用户确认过）**：光照 pass 已经把 GT4 里的 `envSpec = Ind/SpecFactor*occlusion*env` 加进颜色，

`GT4那份 envSpec + X = factor*occl*(env*(1-a) + a*ssr)` ✓ **精确、允许负值（加法混合支持下）**。
⇒ 所以 **GT4 不用改**（保持"emission + 漫反射 + env 高光"），GT5 = 与 GT4 里同一份 `IndirectSpecular(env)`（三通道够了 ⇒ 格式可同 GT4 的 R11G11B10/`RGB111110Float`）。
⇒ 相比"略亮版"，多一张 RT 的显存/带宽，换掉那份 `a*env` 的误差。

**修法**：① 一行 —— 照方向光那样，把 `GetLightingDeferred` 点光循环里的 `RenderingLayersOverlap` 判断去掉（延迟的灯光过滤退化为"只有 `Lighting.cs` 收集时的相机级 mask"，与当前"渲染层先不管"的状态一致）；② 真要做逐像素渲染层，得把掩码塞进 GBuffer（GT2.a 只剩 2 位；GT1.a 被 shadingModelID 占了；GT3 是 R11G11B10 **没有 alpha**）⇒ 工程量大，暂不必要。

### 诊断（2026-09-16，用户问"延迟算阴影用的法线不对吧？怎么简单改"）

**确实不对**：`Surface.interpolatedNormal` 的语义是"**顶点内插法线，不受法线图影响**，用于阴影贴图位移"（`Surface.hlsl:8`）。前向 `LitPass.hlsl:74-79` 正确地分开了（`normal` = NormalTangentToWorld 结果、`interpolatedNormal` = `input.normalWS`）；但**延迟光照 pass**（`CameraRendererPasses.hlsl:103-104`）把**两个都设成 GBuffer2 里那条"带法线图的着色法线"** ⇒ 阴影的法线偏移方向跟着法线贴图走（法线扰动大的地方偏移不对：acne/漏光，且和前向观感不一致）。`ScreenSpacePCSS.shader` 里两处伪造 Surface（:172-176、:351-355）同样是 `interpolatedNormal = normal`（注释还写着"主光PCSS的bias法线用它"）⇒ 一样的问题。

**简单改法（推荐）**：全屏 pass 里用**屏幕空间导数**从重建的世界坐标求"几何法线"，零 GBuffer 改动：
```hlsl
float3 geoNormal = normalize(cross(ddx(surface.position), ddy(surface.position)));
geoNormal *= sign(dot(geoNormal, normal));   // 让它和着色法线同向（叉乘顺序/朝向兜底）
surface.interpolatedNormal = geoNormal;      // 只给阴影偏移用
```
特性/坑：得到的是**逐 2×2 quad 的平面法线**（没有法线图扰动）—— 正是 shadow bias 想要的；几 ALU；**物体边缘**（导数跨到背景/别的物体）会算错 ⇒ 一般 1 像素带的偏差，可接受（要更稳就加"深度差过大则不信任"的兜底）。
**替代方案（不推荐）**：把内插法线也写进 GBuffer —— GT2 是 `ARGB2101010`（a 只剩 2 位）、GT3 是 R11G11B10 没 alpha ⇒ 要动格式，不值。

### 参考：UE / 原神的 SSR 做法（用户贴原文，2026-09-16）

用户问"如果加上 TAA / 动态模糊，那 1 帧差是不是就看不出来了"。结论：**TAA 是最有效的掩盖器**（它本身就是累积历史 8~16 帧 ⇒ 首帧缺失会被历史摊掉、新反射以权重淡入；相机快移时把错位糊成"软"而不是"错"）；**运动模糊只是顺带**（需要运动矢量，且只糊运动方向）；真正的根治是**时域重投影**（按 motion vector 把上一帧 SSR 投到当前帧）——那正是 UE/原神 temporal filter 的作用。代价：TAA/运动模糊都需要**运动矢量**，本项目目前没有 ⇒ 是大工程。

两家做法（要点）：
- **UE**：全屏 SSR，RT = RGBA16_FLOAT；**Hi-Z 加速求交 + 用 roughness 选 HiZ mip**（越粗糙越高 mip = 越糊）；每帧**抖动射线起点 + TAA** 提质量；**命中后采样"上一帧"的 RT** 拿颜色（好处：能反到体积雾/半透明/粒子，代价：无透明深度 ⇒ 拉丝失真）；由 compute（`ReflectionEnvironment` pass）把 SSR **和两个探针的 cubemap 环境反射一起加**到主 RT；探针**启动时烘、只含静态物体**。
- **原神**：SSR 提供探针之外的实时反射，PS4 Pro 上 ≈ **1.5ms**；带 **temporal filter**（当前帧 SSR 与历史混合 ⇒ 更稳更平滑）；为 SSR 生成 **Hi-Z**（单条射线可追到全屏）；用 **Deferred reflection pass** 统一算 Reflection + Ambient，**并把 AO 一起考虑以降漏光**。

**对项目的启示**：① "采上一帧"在业界是常规做法（UE 就是这么干的，还换来"能反射透明/粒子"的好处）⇒ 用户"延迟也用上一帧"的想法有正当理由；② 两家都做 **Hi-Z + roughness→mip + 时域**，我们已具备 mip 链（颜色快照）⇒ 接 roughness→mip 最省；③ 两家都在**专门的合成/反射趟里用自己绑定的探针资源**（cubemap / probe cubemap mip）来加环境反射，而不是读渲染器给的逐物体变量 ⇒ 印证"合成 pass 里想采 env 必须自己喂"。

**"能不能看情况决定要不要 GT5"（用户问）**：**函数签名不能按运行时开关变**（`SV_Target` 个数是**编译期**定的，`out` 参数表只能是固定几个或按**变体/keyword**分两套）。
可做的"看情况"在 **C# 侧绑不绑第 5 张 RT**：
- **推荐**：shader **固定 5 个输出**（`out float3 GT5 : SV_Target4`），C# 只在 `useSSR` 时把第 5 张 GBuffer 绑上/分配；**没绑的那一路写入会被硬件丢弃**（不花带宽、不报错），关 SSR 时另加零成本。
- 更"绝对稳"的替代：GT5 常驻、关 SSR 时写 0（多一路 MRT 带宽）。
- 想省到极致才用 keyword 分两套输出个数（要与 C# 的 MRT 数严格同步，属于隐患，不推荐）。
