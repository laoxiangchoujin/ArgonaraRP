## 排查（2026-09-15）：启动时"间接反射全没" + 开 SSR 后直接光高光看着变弱

**用户报的两件事**
1. pipeline asset 填了 postFX asset、且 SSR 启用时，**刚启动 Unity 看不到任何间接反射（探针的天空反射和 SSR 都没有）**；把 postFX asset 去掉再加回来就恢复。
2. 开 SSR 后似乎 lit 的**直接光高光变弱/消失**。

**我核对过的代码事实**
- **直接光一路完全没被改**：`DirectBRDF` 在光照 pass（`GetLightingDeferred` → `GetLighting`）里，GT1/GT2/GT3 都没动 ⇒ 代码上不可能"删掉直接光高光"。
- 开 SSR 时唯一的变化：GT4 只写 emission + 间接漫反射，间接高光改由 **composite 那趟**补 ⇒ **"间接高光全没" = composite 没生效**（GT4 里没有、它也没补上）。
- `PostFXStack` 里**没有**与 SSR 的任何耦合（`IsActive` 只看 settings 是否非空；`Render(colorAttachmentId)` 在最后一步）。

**给用户的排查方向（按可能性）**
1. **先看 `intensity`（= gain，乘 `ssr.rgb`）是不是 0**：gain=0 会把反射**乘成黑色**（`lerp(env, 0, a)`），视觉上就是"反光没了" —— 新字段的经典坑（asset 里可能没被写成 1）。
2. 帧调试器里确认 `SSR Composite` 那趟在不在、它的 RenderTarget 是不是颜色附件。
3. Console 看有没有 shader / 材质 / pass 相关报错（新 pass 的变体启动时首次编译）。
4. **要问清的关键信息**："重加 postFX asset"到底是**重加那一下**恢复（= pipeline 重建，指向实例初始化状态）还是**保存 asset 那一下**恢复（= 字段值真被写进文件，指向数据问题）。这一条能把范围缩一半。

**Q2 的判断**：直接光高光没被代码删掉 ⇒ 更可能是 (a) composite 没跑 ⇒ 平滑面缺间接高光、整体偏暗（同 Q1）；(b) gain 设太大（他试过 5）把反射区推过曝，tonemap 压缩后直接光的对比度下降。诊断：gain 回 1 / 关掉 SSR 对比一次即可。

## 又一条新证据（2026-09-15）：关 SSR 时，forward 有实时高光、deferred 没有

**结构性事实（很重要）**：关 SSR 时 flag = 0 ⇒ GBuffer 走 `IndirectBRDF`（漫反射+高光，= 老路）、composite 根本不画 ⇒ **deferred 那条链和这次 SSR 改动完全无关**。所以"deferred 少高光"是 **forward vs deferred 的既有差异**，不是 SSR 引入的。

**核对过的一致点**：GBuffer 写的是 `GT3 = (surfaceWS.roughness, metallic, occlusion)`，光照 pass 读的是 `surface.roughness = GT3.x` ⇒ 两边一致（`GetRoughness` 两边同一个来源 ⇒ 不存在"写着roughness读成smoothness"那类错误）。直接光本身两边都走 `DirectBRDF`。

**因此最大嫌疑 = GBuffer 往返的精度**（forward 用顶点/贴图全精度，deferred 用 GBuffer）：
- `_GBuffer2` 是 **ARGB2101010**（法线每轴 10 位）：近镜面高光对法线极敏感 ⇒ 高光会**变淡、变块状、甚至整块错过太阳的小亮斑**；
- `_GBuffer3` 是 **ARGB32**（roughness/metallic 8 位）、`_GBuffer1` 是 **ARGB32**（albedo→F0 8 位）⇒ 峰值被抹。

**要问用户的判别问题**：① 所有物体都没有，还是只有特别光滑/金属的？② 点光源的高光也没有，还是只有主光？③ 是"变淡/块状"还是"完全没了"？④ FD 里 GBuffer 那一步的 GT2/GT3 看着对吗？
**快速实验**：一个球 smoothness=1、metallic=1 —— deferred 下有亮点吗（有 ⇒ 精度问题；没有 ⇒ 逻辑问题）。

## 再更新（2026-09-15）：deferred 连漫反射都没有灯方向响应（forward 正常）

**给用户的三个决定性测试**：① FD 里单看 GBuffer 那步的 GT1.a / GT2 / GT3 对不对；② 光照 pass 里临时把 `shadingModelID` 强制成 1（或跳过解码）→ 灯回来 = ①；③ 关掉阴影 → 灯回来 = ②。

## 定论（2026-09-15）：延迟光照全黑的真凶 = `RenderingLayersOverlap` 在**全屏 pass** 里读逐物体的 `unity_RenderingLayer`

用户测完 ①②③④（position / normal / albedo / GT3）全部正常，怀疑 `GetLightingDeferred`。

**代码比对结论**：`Lighting.hlsl:52-83`（`GetLightingDeferred`）与 `:19-50`（`GetLightingForward`）**逐行一致**，只差两处且都不会导致全黑：① 没有 GI/`IndirectBRDF`（所以他手动加 `emission_indirectColor`）；② `shadowData.shadowMask = gi.shadowMask` 被注释（默认 `shadows=1.0`，等于没有烘焙阴影 → `GetDirectionalShadowAttenuation` 反而因 `strength×global.strength<=0` 走 `GetBakedShadow` 返回 1，**不会压成 0**）。⇒ 函数体不是差异来源，差异在**输入**。

**真凶**：`CameraRendererPasses.hlsl:119` `surface.renderingLayerMask = asuint(unity_RenderingLayer.x);`。`UnityInput.hlsl:4-11` 里它在 `CBUFFER_START(UnityPerDraw)`（**逐物体数据**），而延迟光照 pass 是 `DrawProcedural` 的**全屏三角**，没有"本物体" ⇒ 该值不成立（大概率 0）⇒ `RenderingLayersOverlap` = `(0 & 灯mask) != 0` = false ⇒ **每盏灯都被 if 挡掉，`GetLighting` 一次都不执行 ⇒ 全黑**。
与全部观测自洽：方向光黑 ✓ 点光也黑 ✓（同一个门）；`GetDirectionalLightCount()` 正常 ✓；四项 GBuffer 输出正常 ✓（都不碰该变量）；forward 正常 ✓（真实物体绘制时 `unity_RenderingLayer.x` = 物体的 `m_RenderingLayerMask` = 1 → `1&1` 通过）。
C# 侧无一致性问题：`Lighting.cs:148/161/173` 用 `light.renderingLayerMask.ReinterpretAsFloat()` 把**位模式**写进 `.w`，shader `asuint` 取回 1 ✓（灯侧没问题，坏在"表面侧"没有值）。

**修法（待用户确认后再改）**：延迟光照 pass 不用逐物体值，改由 `CameraRendererDeferred` 在光照 pass 前上传全局量（摄像机的 layer mask 近似），或延迟里不做这个门。

## 已确认 + 根因解释 + 解法（2026-09-15）

**用户实测确认**：把 `GetLightingDeferred` 里的 `if (RenderingLayersOverlap(surfaceWS, light))` 注释掉，延迟下直接光就正常了 ⇒ 上面的定论成立。

**为什么不稳定的"以前没事、今天才遇到"**：
- `unity_RenderingLayer` 属于 `UnityPerDraw`（逐物体），**全屏 `DrawProcedural` 里这个值是"未定义"** —— 引擎不为 procedural draw 填它，实际拿到的是上一个写 per-draw 数据的 draw 的残留（可能是 1，也可能是 0）。
- **前向是结构性正确的**：光照 pass 跟着真实物体绘制，每个物体绘制都刷新该值为物体的 `m_RenderingLayerMask`(=1) ⇒ 永远对。前向里那些全屏 pass（屏幕空间阴影）都排在物体绘制**之前**。
- **延迟是结构性不可靠的**：光照 pass 前面只剩全屏 pass（GBuffer 物体 → `DrawScreenSpaceShadow` 那 5 趟全屏 → 光照）⇒ 值由"上一个全屏 draw 留下什么"决定。用户以前凑巧拿到残留的 1，最近加了 PCSS 屏幕空间阴影（+SSR/拷贝颜色）改了 pass 顺序和数量，侥幸破了。
- 灯的 `.w` 侧无问题：`Lighting.cs:148/161/173` 用 `light.renderingLayerMask.ReinterpretAsFloat()` 写位模式，shader `asuint` 取回，成对一致。

**解法**：
- **A（推荐，最小且稳）**：延迟光照 pass 不读 `unity_RenderingLayer`，改由 `CameraRendererDeferred` 在光照 pass 前 `buffer.SetGlobalFloat(id, BitConverter.Int32BitsToSingle(mask))`（位模式，配 shader 的 `asuint`），mask 用"和 C# 端过滤灯光同一个值"（`cameraSettings.maskLights ? cameraSettings.renderingLayerMask : -1`）⇒ 该判断对已存灯必然为真，等价于"已在 C# 过滤"。
- **B（一行）**：延迟里直接删掉这个门（延迟本来做不了逐物体光层，C# 端已按相机 mask 过滤过灯）。
- **C（URP 做法，不建议现在做）**：按 light layer 分组 + stencil，把全屏光照 pass 多画几遍。
- **必须一起修**：延迟里 `#if defined(_LIGHTS_PER_OBJECT)` 分支读 `unity_LightData.y`（同为逐物体，全屏 pass 里为 0/未定义）⇒ 点光循环跑 0 次 ⇒ **点光源在延迟下永远不亮**。延迟必须强制走 else（遍历所有其他光）。

## 追问：延迟要真正支持光层，怎么做（2026-09-15）

用户理解正确（并补充精确说法）：`unity_RenderingLayer` 不是"按像素写屏"，而是**逐 draw 的常量**（UnityPerDraw）——**一次 draw 内所有像素共享一个值**。前向 = 一个物体一趟 draw ⇒ 每个物体的像素自带自己的层；延迟 = 一趟 draw 覆盖整屏 ⇒ 只有一个值，且来源不可靠。

**方案的可行性结论**：
1. **写进 GBuffer：可行，且是正路**（HDRP 就是专门存 rendering layer mask）。现有 GT1~GT4 已满（albedo / normal / rough-metal-occl / emission），需加一张 R8/R16（8/16 层）或挤占现有通道的位。有了 per-pixel 层掩码后，**当前"单趟全屏光照 pass + 逐灯 & 判断"的结构就完全够用**，不需要逐灯多趟。
2. **Stencil：思路对但要分两种**。
   - **读不出值**：Unity shader 无法把 stencil 当纹理采样（没有 SRV），所以"写 stencil + 光照 pass 读它"走不通 ✗。
   - **可以做"多趟 + 掩码"**：把层掩码写进 stencil（8 位 → 8 层），光照 pass 画 N 遍，每遍 `Stencil Comp Equal Ref=i` 只放第 i 层像素通过 —— 这是 URP 处理 light layers 的做法；代价是 N 趟全屏。
   - 本项目延迟目前是单趟全屏、没有 per-light stencil 卷 ⇒ stencil 是空的、可用；但 8 位限制层数。
3. 结论：最省事 = 延迟不做这个门（相机层近似，方案 A/B）；要真做 = per-pixel 层掩码进 GBuffer。不建议现在动。

## 现有 GBuffer 布局（代码核对，2026-09-15）

`CameraRendererDeferred.cs:280-299`（注释表）+ `LitPass.hlsl:121-186`（写入）：
- GT1 `ARGB32`：albedo.rgb + A = `ShadingModelID(4b) + 空(4b)`（写入 `((uint)1<<4)/255`）
- GT2 `ARGB2101010`：normal.xyz + A 2 位（注释写 `_ReceiveShadows(1b)+空(1b)`，但**实际写的是 `0.0`** ⇒ 这 2 位现在都空着、可用）
- GT3 `ARGB32`：**(roughness, metallic, occlusion, 0)** —— 注意注释写的是 smoothness，代码写的是 roughness（注释与代码不一致）；A 空
- GT4 `RGB111110Float`：emission + 间接光，**R11G11B10 没有 A 通道**（"A 空"不成立）

**层掩码放哪的结论**：
- Unity `renderingLayerMask` 是 32 位；**掩码语义下"位数 = 层数"**（4 位掩码 = 只有 4 层，不够）；"4 位 = 16 层"是**索引语义**（存层号 0~15，物体只能属于一层），需要把测试改成 `(1u << surfaceLayerIndex) & light.renderingLayerMask`。
- 方案：① 4 位**索引**放 GT1.a 低 4 位 → 16 层、零成本（用户的想法，可行）；② 加一张 R8/R16 GBuffer → 8/16 层**掩码**（保留"物体可多层"语义）；③ 32 位掩码需一张 R32 或分两通道。
- **stencil 多趟的本质**：遍数 = 屏幕**层值种类数**（不是物体数）；一遍全屏只处理"层值==i"的像素（其余被 stencil 测试挡掉）。最坏情况（每物体一层）才会爆。⇒ 写 GBuffer 单趟更划算。

## 编码方式的选择：Unity 用掩码，本项目也用掩码（2026-09-15）

**已核实**：`Library/PackageCache/com.unity.render-pipelines.core@16.0.6/ShaderLibrary/CommonLighting.hlsl:501` → `bool IsMatchingLightLayer(uint lightLayers, uint renderingLayers) { return (lightLayers & renderingLayers) != 0; }` ⇒ Unity/core RP = **掩码编码**，两侧都是 uint(32 位)。URP 的 light layers 是 8 层掩码（`LightLayerEnum` = `1 << i`），HDRP 的 LightLayers 也是 8 层；生态里没有引擎用索引编码。

**给用户项目的推荐（他偏好简单好操作）**：保持**掩码语义**，8 位掩码放 **GT3.a**（`CameraRendererDeferred.cs` 里 GT3 是 ARGB32、A 写死 `0.0`，完全空着）。
- 存：`GT3.a = (float)((uint)renderingLayerMask & 0xFF) / 255.0;`
- 读：`uint layerMask = (uint)(GT3.a * 255.0 + 0.5);`（GT3 用 `RenderTextureReadWrite.Linear` ⇒ 无 sRGB 曲线，8 位可精确表示 0~255）
- 好处：8 层、不动格式/不加 RT/不加带宽、`RenderingLayersOverlap` 与前向代码**一字不改**（灯侧仍是 32 位掩码，`&` 时高位自然被忽略）。
- 索引编码（4 位 = 16 层）虽省位，但要改 shader 测试 + GBuffer 写入 + C# 过滤三处，且丢掉"物体可多层"，不符合"简单"目标。
- 将来要更多层：再拿 GT1.a 低 4 位（凑 12）或加一张 R8/R16。

## 参考：HDRP GBuffer 布局（用户要求，2026-09-15）

本机**没装 HDRP**（PackageCache 只有 core 16.0.6），官方文档页 404；下表来自引用 **HDRP 6.7** 的资料（经典布局，社区广泛引用）：

| Buffer | 格式 | RGB | A |
|---|---|---|---|
| GBuffer0 | RGBA32 | Albedo Color / SSS Color | Specular Occlusion / SSS Parameter |
| GBuffer1 | RGBA32 | Packed Normal（打包法线） | Roughness |
| GBuffer2 | RGBA32 | BSDF Model Specific Parameters（各向异性/虹彩/透光等） | Coat Mask + Material ID |
| GBuffer3 | R11G11B10 | GI + Emissive | 无 A |
| GBuffer4（可选） | RGBA32 | R:/ G:/ B: AO | **Light Layer** |

### 【重要更正】之前说"URP 用 stencil 存 light layers + 按层多趟全屏"是**错的**

已抓取 URP 源码 `Packages/com.unity.render-pipelines.universal/Runtime/DeferredLights.cs`（master）核对：
- **URP 的 rendering layers 存在独立的 GBuffer slice**：`GBufferRenderingLayersIndex => UseRenderingLayers ? 5 : -1`，格式由 `RenderingLayerUtils.GetFormat(RenderingLayerMaskSize)` 决定 ⇒ **层数（8/16/32）直接决定 RT 格式（R8/R16/R32）**，掩码语义，不挤位。`UseRenderingLayers => UseLightLayers || UseDecalLayers`；只开 decal layers 时复用 `resourceData.renderingLayersTexture`；还有可选的 `HasRenderingLayerPrepass`。
- 灯侧：**逐灯全局 uniform** `_MainLightLayerMask` / `_LightLayerMask`（`SetRenderingLayersMask`）+ 全局关键字 `LightLayers`；**层判定在像素着色器里做位与**。
- **全屏光照 pass 是"逐灯"不是"逐层"**：每盏方向光固定 2 趟（Lit + SimpleLit），点/聚光每盏 = 1 趟 stencil volume + 2 趟；Deferred+（clustered）只有 2 趟全屏。⇒ 我之前说的"遍数 = 层值种类数"作废。
- URP 的 stencil 只承载**材质位**（MaterialLit/SimpleLit/Unlit/MaterialMask）与 `StencilLight`（体积裁剪），没有 LightLayers 位。
- 注意：多一个 slice 会影响 MRT 上限（`GBufferSliceCount <= SystemInfo.supportedRenderTargetCount`，移动端敏感）。

HDRP 的 stencil 也已排满（`HDStencilUsage.cs`：bit0 IsUnlit / bit1 RequiresDeferredLighting / bit2 SSS / bit3 TraceReflectionRay / bit4 Decals / bit5 ObjectMotionVector，透明阶段复用为 WaterExclusion/ExcludeFromTUAndAA/Distortion/Refractive/WaterSurface，bit6-7 是 UserBit0/1）⇒ 所以 HDRP 的 Light Layers 只能放 GBuffer。

**统一结论**：Unity 两家都是「**GBuffer 存 per-pixel 层掩码 + 像素着色器里逐灯按位与判定**」，与本项目现有结构完全一致，只缺 per-pixel 那几位数据。扩层数的正规做法 = 加一张对应宽度的 RT（R8/R16/R32），而不是挤位。

## 转向：SSR 闪烁 —— 按 mip 采样颜色纹理（2026-09-15，方案已定，待动手）

用户放弃渲染层，转去解决 SSR 闪烁，方向选定"按 mip 采样 `_CameraColorTexture`"。

**已核实现状**
- SSR 四趟全在延迟：trace（半分辨率 `SSRPass.Trace`）→ 横/纵 ±2 纹素 blur → composite（`Blend One One` 加回颜色附件）。`DrawSSR` 在第二次 `CopyColorAttachments(true)` 之后 ⇒ `_CameraColorTexture` 的 mip 链在 trace 前已就绪；**前向没有 SSR**（`CameraRendererForward.cs:44`）⇒ trace 里读 `_GBuffer3` 取 roughness 合法。
- 闪的主因：`SampleReflectionColor`（`ScreenSpaceReflection.hlsl:304`）**固定 LOD 0**，而 trace 每像素只有一次 4×4 抖动 + 1 像素步进 ⇒ 命中点抖动原样进颜色；两趟 blur 太小抹不平；同时环境反射（`GI.hlsl:158`）已按粗糙度取 mip（`PerceptualRoughnessToMipmapLevel`）⇒ "环境糊、SSR 锐"，`GI.hlsl:175` 的 lerp 把锐利抖动透出来。
- `SSRSettings` 里可加新调参（已有"合成 & 质量"段）。

**分步方案**
- 第 1 步（小）：`SampleReflectionColor(hitPixel, lod)`；TracePassFragment 读 `_GBuffer3.x` 当 roughness，`lod = scale*rough + bias`；`SSRSettings` 加 `roughnessMipScale/Bias` 并在 `SetSSRParameters` 上传。注意 `copyColorMipCount` 要调到 6~8（默认 5 只到 1/16）。mip 间要平滑需把采样器换成按纹理命名那个（RT 建的是 Trilinear）。
- 第 2 步（正确口径）：足迹/锥 —— `lod = log2(max(1, rough*hitZ / 单像素世界尺寸(hitZ))) + bias`；`tanHalfFov` 由投影矩阵 `_m11` 反推。
- 第 3 步（若仍闪）：按粗糙度给 SSR 混合权重降权（粗糙面以环境反射为主），或平滑 `alphaCalc` 的可信度。

**第 1 步的参数口径（答疑，未动手）**
- `lod` 的有效上限 = **mip 级数 - 1**（8 级 = 0~7）。所以"rough=1 采到最糊那级" ⇒ `roughnessMipScale = 级数-1`（8 级就是 7；填 8 等价，会被 clamp）。`roughnessMipBias` 默认 0，只是整体平移（正=更糊）。实际调：先按上限看"最粗糙是否不闪"，再往下收到 4~5 找"不闪 + 还清楚"的平衡。
- **跨 mip 级的跳变会造成闪**：`sampler_linear_clamp` 的 mip 过滤是"点"的 ⇒ lod 小数被取整；lod 本身由粗糙度/命中距离/命中点（都在抖）算出来 ⇒ 在 x.5 边界附近会在两级间跳，把抖动放大。修法：① 用按纹理命名的采样器（RT 建的是 Trilinear）② 自己采两级 floor/frac 手动 lerp（更稳，多一次采样）。级数越多、相邻级差异越小，跳变越不明显。
- 本步仍不是物理正确（不考虑距离）⇒ 想一次到位直接上第 2 步的足迹公式。

## bug（2026-09-15）：开 mip 且级数≥2 时，SSR trace 采到的颜色纹理是黑的

- ⚠️ **前向的 `CopyAttachments()` 有一模一样的写法**（同样的潜在 bug，只是前向 SSR 还没做、没暴露）—— 已告知用户，等他决定要不要一起改。

### 已做（2026-09-15）：SSR 消萤火虫（亮度反向加权 blur + 开关）

用户要求：就做 `w = 1/(Luminance(c)+1)`、**不加参数 k**，但要一个开关。
- `Shaders/ScreenSpaceReflection.hlsl`：两趟 blur 改成加权平均 —— 每抽头 `w = kernel[i+2] * lerp(1.0, 1.0/(SsrLuminance(c.rgb)+1.0), _SSRFireflySuppression)`，`sum += w*c`、`weightSum += w`，**返回 `sum / max(weightSum, 1e-5)`**（权重和不再为 1）。
  亮度式子用 `dot(color, float3(0.2126,0.7152,0.0722))`，定义为文件内的 `SsrLuminance()`（**故意不用 core 的 `Luminance`，避免撞名**）；`_SSRFireflySuppression` 声明在 blur 之前（HLSL 先定义后使用）。
  开关关掉时 `lerp` 给 1 ⇒ 权重和恰好 = 1 ⇒ 与改动前逐像素一致（零成本开关）。
- `Runtime/SSRSettings.cs`：新增 `public bool fireflySuppression = true;`（在 intensity 之后，带 Tooltip）。
- `Runtime/CameraRendererDeferred.cs`：新增 `ssrFireflySuppressionId` + 在 `SetSSRParameters()` 上传 `? 1 : 0`。
- `Assets/Settings/Argonara Render Pipeline Asset.asset`：`ssr:` 块写入 `fireflySuppression: 1`（用户把 `roughnessMipScale` 自己改成了 3）。
- 固有代价（要记住）：按亮度反向加权会**顺带轻微压暗弥散的亮区域**（不只压孤立亮点）⇒ 反射亮度分布变平；若觉得压过头，就加回 `k`（`1/(L*k+1)`）。
- 备选未做：firefly clamp。

### 追加（2026-09-15）：压亮度强度 k 已加（用户嫌压太多）

- `SSRSettings` 新增 `[Range(0,5)] float fireflyStrength = 0.5f`；`CameraRendererDeferred` 上传 `_SSRFireflyStrength`；asset 写 `fireflyStrength: 0.5`。
- shader 两趟 blur 的权重改为 `w = kernel[i+2] * lerp(1.0, 1.0/(Luminance*k + 1.0), _SSRFireflySuppression)`。
  **k = 0 ⇒ 完全不压（等价于关掉开关）；k = 1 ⇒ 卡特莱克原式；k 越大压得越狠。**

### 分析（2026-09-15，未改代码）：SSR 的 Fresnel 权重 + 追踪的三个可选改进

**1) "阶段2 物理融合（Fresnel+smoothness → EnvironmentBRDF）"我们其实已经做完了** —— 就是 `BRDF.hlsl` 的 `IndirSpecFactor`：
`surfaceReduction(1/(roughnessSquare+1)) * lerp(F0, grazingTerm, Pow4(1-NdotV))`，`F0 = lerp(0.04, albedo, metallic)`。
`IndirectSpecular = giSpecular * IndirSpecFactor * occlusion` ⇒ **Fresnel（F0 + 掠射）已经在乘，和 URP 的 EnvironmentBRDF 同一套**。
用户观感"SSR 强度只跟 smoothness 有关"的原因：① 菲涅尔乘在**最后**（作用于 env+SSR 整体），不在 `lerp(env, ssr, a)` 的替换率上；② 掠射角恰好被 `alphaCalc` 的淡出抹掉，两个效应互相抵消。
⇒ **不要"再补一层菲涅尔"**（9-14 已明确：别处再乘 = 双重加权、掠射角变暗）。唯一有意义的变体是按 rough 分配 SSR/env（"锐利给 SSR、模糊给探针"），但 9-14 已验证粗糙面镜面权重本就极小 ⇒ 收益低，不值得。

**2) 追踪三个改进的现状**
- **自适应厚度**：**没有**（`intersect` 里固定 `_SSRPixelThickness`）。值得改（2 行）：`thickness = max(_SSRPixelThickness, k*|rayStepB - rayStapA|)`（k≈0.5~1），因为我们的步长是变的（近处 ×2）⇒ 固定厚度会"一步跨过薄物体"= 反射断续/漏交。代价：厚度大 ⇒ 把背景误判为命中（拉丝）。
- **射线终点截到近平面**：**没有**（`traceRay` 里 `if (currentZVS < 0) return false` 直接放弃）⇒ 近处/朝相机方向整块硬切回 env。改法：把 endVS 夹到近平面前、重算 delta，2~4 行；收益中等、与闪烁无关 ⇒ 优先级低。
- **自交处理**：**已有**（`prev1bz = current1bz + 0.1*delta1bz`，"沿射线推 0.1 步"）。二选一的话"固定 0.1 米深度 bias"更稳（不受步长影响），但除非有"起点自反射圈"症状，否则不必动。

**3) 自适应厚度的具体做法（已给方案，未动笔）**
- 原理：`intersect` 现在拿固定 `_SSRPixelThickness` 当"物体有多厚"。**一步跨过的深度比自己厚度还大时，射线会整步跳过那个 slab（隧穿）** ⇒ 漏交/断续。所以厚度不能小于"这一步的深度跨度"。
- 最小改法（`intersect` 内，3 行）：`thickness = max(_SSRPixelThickness, _SSRThicknessStepScale * (rayStepB - rayStapA))`（`Swap` 已保证非负），k 新增为参数、默认 0.5~1。
  - 只影响**大步进阶段**：二分那 6 次的 `rayStapA/rayStepB` 跨度很小，自适应项自动变小 ✓ 正是想要的。
- 精修版（治倾斜表面/近处步长大）：再 `+ |∂linearDepth/∂pixel| * pixelsPerStep`（因为我们是隔 N 像素抽样比较，倾斜面本身每像素的深度变化会被误判成隧穿）⇒ 要算 `ddx/ddy`（便宜，本项目别处也这么用）；先做最小版，症状还在再上。
- 两个约束：① 要有**上限 clamp**（步长特别大时不能无限放宽，否则假命中）；② `_SSRPixelThickness` 退化为**下限**。
- 用户看过方案后决定**先不做**（"意义不明"）。

### 现状盘点（2026-09-15）：SSR 还缺什么（用户问，未动笔）

**已经有的**：延迟下的 trace（半分辨率 + 4×4 抖动 + 二分 6 次 + 背面剔除 + 四项淡出）、两趟 blur（含消 firefly）、roughness→mip、间接高光合成 pass（同帧）。
**还缺的（按优先级）**
1. **时域累积**（最大）：现在每帧只有 1 条抖动射线，抖动是**固定 4×4**（不能逐帧旋转）⇒ 降噪只能"一次采样+模糊"，要么糊要么闪。做成"持久双缓冲 + 逐帧旋转抖动 + 历史 reprojection/clamp"能同时：治闪、提分辨率、降噪。**代价：需要运动向量**（GBuffer 没存）——相机运动可用深度+上一帧相机矩阵近似重投影，代价是**动态物会 ghost**。
2. **Hi-Z 步进**（层级深度）：现在固定像素步长（4）+ 步数上限 64 ⇒ 长射线被截断（反射不够远/漏交），大步长本身就是漏交根因。Hi-Z 能用很少采样走很远 ⇒ 更远、更准、更快。
3. **前向路径没做**（纯工程量，现在前向的物体只能靠上一帧图）。
4. 次级：粗糙度加权的 SSR/env 混合（现在是 `lerp(env, ssr, a)` 硬替换）、射线终点截到近平面、lod 的"足迹/锥"口径（现在是 `rough*scale` 线性）、半分辨率上采样质量、水面等透明接收面、反射源只有环境探针。

### 前向 SSR 的实施方案（2026-09-15 已给用户，未动笔）

**已定前提**：前向**只用上一帧**的 SSR 图 ⇒ 不需要拆间接高光、不需要 composite pass；前向的 Lit 自己用 `SampleEnvironment(surface, brdf, uv)` 3 参变体融合。
**流程（4 步）**
0. **把 SSR 的图从"每帧临时"改成"跨帧持久 + 双缓冲"**（这是"上一帧"的前提）：两张半分辨率 HDR（A/B）由渲染器持有，尺寸/格式变了就重建、`Dispose` 释放；blur 的倒手图仍可每帧临时。每帧决定"读哪张（上一帧结果，`SetGlobalTexture(_SSRTex, 读的那张)` 给不透明物）、写哪张（trace/blur 写它）"，帧末交换。**别用同一张既读又写**（Unity 会报 read-write same RT）⇒ 双缓冲最省心。
1. **抽公共部分**：material + `SetSSRParameters()` + "trace+两趟 blur"三步绘制（图由调用方给）。延迟保持"临时图、同帧用"不动，**别为共用强行改延迟**（两者图的**生命周期**不同）。
2. **前向接"读"**：`LitPass.hlsl` 的 `LitPassFragment`（前向）改用 3 参 `SampleEnvironment`（屏幕 UV 从 `positionCS_SS` 拿）；每帧必须把 `_SSRTex` 绑成上一帧那张，**没开 SSR 时绑 missingTexture**（否则采到已释放的图）。前向不读也不设 `_UseScreenSpaceReflectionInDeferred`（保持 9-14 的定案）。
3. **前向跑 trace 的时机与依赖**：画完**不透明 + 天空盒 + 拷颜色**之后、画透明之前（本帧颜色当反射源；透明物也能采上一帧图）。
   - 依赖：`_CameraColorTexture`（带 mip ✓）、`_CameraDepthTexture`（copyDepth ✓）、**法线图** —— ⚠️ 前向的法线图现在只有屏幕空间阴影开着才生成 ⇒ 门要改成 `useScreenSpaceShadow || useSSR`。
   - ⚠️ **roughness→mip 在前向拿不到**（没有 GBuffer，全屏 trace 查不到每像素粗糙度）⇒ 先让前向的 lod 固定 0；要画质就把粗糙度写进 DepthNormals 预pass 的法线图 A 通道。
**固有代价（要提前说清）**：1 帧延迟 + 屏幕空间采样 ⇒ 相机一移动，反射图会**整体滑动/拖尾**（相机静止时最好）。这不是 bug。

```hlsl
// return float4(dbgSsr.a, 0, 0, 1); // ② 可信度：0=全被淡出吃掉
```
1. **均匀 0.5 灰** ⇒ Lit 拿到的 `_SSRTex` 是 missingTexture（`a=0.5` 正好会把 env 拉向灰=“更亮”）⇒ 查绑定时机 / `useSSR` 在那一刻是否真为 1；
2. **图正常但 `a`≈0** ⇒ 可信度被 `alphaCalc` 的四项淡出吃掉 ⇒ 调那几个淡出参数（或 intensity）；
3. **图正常、a 也正常** ⇒ 就是观感/权重问题（`_SSRIntensity` 偏大 + 图偏亮 ⇒ 整体发亮），把 intensity 拉回 1 对比。
另外让他顺手看：帧调试器里 trace 那一步的**源 `_CameraColorTexture` 是不是场景快照**（若是纯灰 ⇒ `copyColor` 没开，反射源本身是空的）。

**测试结果（用户）**：① Lit 里 `SAMPLE_TEXTURE2D(_SSRTex, ...)` 的 **rgb 和 a 都是 0（全黑）**；② trace 那一步的源 `_CameraColorTexture` **确实是场景快照**（所以反射源没问题）。
**推理**：`missingTexture` 是 0.5 灰 ⇒ Lit 采到的**不是空纹理**，而是"真的反射图、但内容全 0"。严格全 0 最符合 **trace 在第一个门槛就统一早退**：
`if (rawDepth < 0.00001) return 0.0;` ⇒ 只要 `_CameraDepthTexture` 在前向是空的/没绑，**整张输出必然全 0**（rgb=a=0）✓✓
⇒ 头号怀疑：**前向里 `_CameraDepthTexture` 是空的**。它的来源只有两条：`CopyAttachments()`（门 = `useDepthTexture && !useScreenSpaceShadow`）或 `DrawScreenSpaceShadow()` 第②步 ⇒ 先确认 `copyDepth`（管线资产 + 相机设置）开着；或在 trace 里临时 `return float4(rawDepth.xxx, 1)` 直接看深度输入。
次要怀疑：Lit 的 `config.fragment.screenUV` 与实际采样对不上（若采到贴图边缘，而边缘恰好全 0 —— trace 对出屏/边缘像素正是 `return false` ⇒ a=0）⇒ 一行验证：Lit 里 `return float4(config.fragment.screenUV, 0, 1);` 看是不是 0→1 的正常渐变。

## 真凶（2026-09-15）：`rt.format != format` 让两张持久图**每帧**被销毁重建

用户反驳"多相机重建只会影响一帧，且一直待在 Game 里也不对"—— **反驳正确**，我第一版分析不成立。


## 待办（用户要求记录）：前向的 SSR **没有**按粗糙度取 mip ⇒ 反射永远清晰

**现状（2026-09-15 确认）**：trace 里 `receiverRoughness = _UseDeferredRenderer > 0 ? 采 _GBuffer3 : 0` ⇒ **前向的 lod = max(bias,0) = 0（mip0），永远是最清晰那一档**。
⇒ 前向的反射该糊的地方不糊（粗糙面照样锐），firefly/抖动只能靠那两趟 blur 和亮度反向加权顶着，比延迟（有 roughness→mip）明显更容易闪。
根因：trace 是**全屏 pass**，拿不到每个像素的接收面粗糙度（前向没有 GBuffer；法线图 `ARGB2101010` 的 A 只剩 2 位，塞不下粗糙度）。

**解法（推荐、且比"把粗糙度塞给 trace"简单得多）**：**改在"采样端"算 lod** —— 前向是 **Receivers 自己采 `_SSRTex`**（`LitPassFragment` 里的 `gi.specular = SampleEnvironment(surface, brdf, uv)`），而 **Lit 本来就知道本像素的 `surface.roughness`** ⇒ 不需要把粗糙度送进 trace，直接在 Lit 里按粗糙度取 mip：
```hlsl
float lod = max(_SSRRoughnessMipScale * surface.roughness + _SSRRoughnessMipBias, 0.0);
gi.specular = SampleEnvironment(surface, brdf, config.fragment.screenUV, lod);//三参变体加个 lod 形参
```
配套（都在前向，约 5 处小改动）：
1. 两张持久图改 `useMipMap = true` + 给 `mipCount`（半分辨率，代价小）；
2. `filterMode` 用 **Trilinear**（自己 new 的 RT 说了算），采样器用按纹理命名的那个（`SAMPLER(sampler_SSRTex)`），避免 mip 之间"取整跳变"；
3. `DrawSSR` 两趟 blur 之后再 `buffer.GenerateMips(ssrTextures[...])`（半分辨率，一趟便宜）；
4. `GI.hlsl` 三参 `SampleEnvironment` 加一个 `lod` 形参（HLSL 无默认参数 ⇒ 延迟的合成 pass 传 0，行为不变）。
优点：粗糙度是**接收面**的属性，本来就该在接收端算；前向拿得到精确值，也不用动预pass/GBuffer。缺点：多一条 `GenerateMips`（半分辨率）+ 一点点显存。

## 【存档·用户要求】前向 SSR 相对延迟的差异 / 未做点 / 注意事项（2026-09-15）

**A. 架构性差异（设计如此，不是 bug）**
1. **时间关系**：延迟 = 同帧（trace→blur→composite 都在本帧，不透明体与水面当帧就能采到）；前向 = **本帧追、下一帧用**（Lit 采 `ssrTextures[ssrReadIndex]` 是上一帧图）⇒ 相机移动/转身时反射"拖、黏"（屏幕空间鬼影），这是**最大的观感差异**。两张持久 RT 双缓冲，`ssrReadIndex` 的交换**只能在 `DrawSSR` 末尾**（放 `AllocateSSRTextures` 里会让双缓冲永不交换）。
2. **合成方式**：延迟有第 4 趟 `SSRPass.Composite`（读 GBuffer 重算 `IndirectSpecular`，`Blend One One` 加回颜色附件；开 SSR 时 GBuffer 那趟的 GT4 **不写**间接高光）；前向**没有合成趟** ⇒ 由 Lit 自己 `gi.specular = SampleEnvironment(surface, brdf, screenUV)` 用 SSR 替换环境反射。
   ⇒ 后果：前向**只有走了这套 Lit 的物体**才有 SSR 合成（Unlit / 其他 shader 不采）；延迟的合成是对全屏颜色加性混合，覆盖面更广。
   （注：`CameraRendererDeferred` 里 `SSRPass.Composite` 的注释"shader里目前还是**空占位**，C#还没画它"已**过时** —— 代码 :506-507 确实在画 pass 3。）
3. **输入来源不同**：延迟直接读 GBuffer（`_GBuffer2` 法线全精度、`_GBuffer3.x` = 接收面 roughness）；前向靠 `DrawDepthNormalsPrepass` 写 `_CameraNormalsTexture`（`ARGB2101010`，法线/轴只有 10 位，编码 `n*0.5+0.5`）+ **必须 `useColorTexture`**（反射源颜色快照）。
   ⇒ 前向**多一趟全屏 prepass 开销**、**法线精度更低**（背面剔除 & 反射方向略糙）。该 prepass 与屏幕空间阴影共用（`if (useScreenSpaceShadow || useSSR)`）。

**B. 明确"没做"的点**
1. **粗糙度→mip 缺失（前向）**：见上一条待办（`receiverRoughness` 恒 0 ⇒ lod = bias = mip0，永远清晰、糊不了、更易闪）。
2. **没有"per-pixel 接收面属性"的承载位置**（法线图 A 只剩 2 位）⇒ 任何"按接收面粗糙度/层/材质变模糊、变强度"的效果在前向都做不了，除非改 depth-normal prepass 的输出格式或另开一张图。
3. 没有 composite（= 没有 GBuffer）⇒ 想调"SSR 如何参与间接高光"，只能改 `GI.hlsl` 的三参 `SampleEnvironment`。

**C. 注意事项（容易踩）**
1. `_UseScreenSpaceReflectionInForward` / `_UseScreenSpaceReflectionInDeferred` 是**两个**开关（因为"有没有图"两边时机不同），shader 里判定是**"或"** ⇒ **每帧都必须显式设**，关掉时必须写 0；否则残留的 1 会让 Lit 去采一张空纹理（1×1 灰）⇒ 高光发灰。
2. 前向 `useSSR` 的前置条件比延迟多一条 **`useColorTexture`**（没颜色快照就直接关 SSR，避免采灰图）；两边都排除 `CameraType.Reflection`（探针不跑：cubemap 投影下"反射方向"无意义 + 6 次/帧）。
3. 持久 RT 的坑：判断"参数变了没"**不能拿 `rt.format` 比**（请求 Default/DefaultHDR 时平台会解析成具体格式 ⇒ 每帧判"变了"⇒ 每帧重建 ⇒ 图永远空）；新建图内容未定义，`AllocateSSRTextures` 里必须 `ClearRenderTarget` 一次，否则首帧/重建帧把垃圾当"上一帧结果"。
4. 释放口径：两张反射图是**持久**的（只在"开关关掉"或 `Dispose` 释放）；`_SSRTex_TempBlur` 倒手图是**临时**的（`Cleanup` 里 `ReleaseTemporaryRT`），关掉时 `_SSRTex` 必须绑 `missingTexture`。
5. 尺寸：两张都是 `bufferSize/2` 半分辨率（两边一致）；`_SSRTexelSize = (1/w, 1/h, w, h)`，blur 按它取邻居。
6. 前向若开 MSAA（延迟本就不支持）：SSR 的输入拷贝都是 `msaaSamples = 1` 的临时图 ⇒ 与 MSAA 边缘不匹配，半分辨率放大处的走样会更显眼。（**未实测**，留作注意项。）

**D. 一句话定位**：前向 SSR = "能用、尽力而为档" —— **晚一帧** + **清晰档（无粗糙度模糊）** + **只对 Lit 生效** + **多一趟法线 prepass**；延迟 SSR 才是全功能档。用户已定调：**不再为前向补这些**。
